# 提出を終えたことを明示し、次の工程へ渡す

**提出終了を明示する機能を、実行をつなぐ補助として採用しました。** 実AIの改訂13分29秒・別評価6分13秒で、両担当が終了を明示し、保存内容を保持したまま次工程と結果回収へ進めました。正式な改訂案1件・別評価1件を保存しています。デッキ案の試用推薦は0件で、システム全体は未完成です。

前の試行では、正式提出と報告後も担当が自然終了せず、約4分11秒待って期限停止しました。今回は担当の終了操作を受け、提出の対応と保存内容を確認して停止させ、停止後にも同じ内容かを検査します。実AIで終了操作の受付から工程終了までは改訂0.535秒・評価0.446秒でした。担当が終了を明示するまでの時間は別で、改訂では最後の報告から工程終了まで21.264秒です。

検証は、開始前に[判定条件](protocol.json)と[実AIの入力・上限](live-protocol.json)を固定し、次の順で行いました。

1. 通常の自然終了も保つ任意の機能として実装。未提出・入力改変・期限との競合・子処理の残留などを検査し、別担当が終了前後の境界を点検しました。本体反映後の機能171件と型検査が合格しました。
2. 保存済みの改訂2とその別評価を入力に、改訂15分・続く別評価10分を上限として一度だけ実行。両担当の正式提出・提出後の報告・終了操作・停止と再検査を記録しました。
3. 元入力・固定実装・以前の正式保存物が保たれたこと、今回の提出者と資料の対応、停止処理の記録と本体台帳への時刻反映を照合。正式な保存一式と公開操作を回収しました。

改訂側には終了後、実行側が評価用資料を1件追加しています。そのため終了時点の要求を現状態へそのまま再適用した最初の回収処理は停止しました。追加資料が今回の評価入力と全文一致し、他の保存物が変わっていないことを確認してから、検証用の複製で終了時点の状態を再検査しました。元ファイルは変えず、[回収失敗と修正した照合手順](collection-recheck.json)も残しています。
