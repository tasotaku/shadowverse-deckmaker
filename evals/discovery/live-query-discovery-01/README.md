# 考案中に検索できることが、案の発展につながるか

**検索入口なしは9月13日07:10:22、入口ありは07:10:31（日本時間）から考案中です。実際に渡した初回入力の一致を確認しました。方法の有用性と採否は未判定で、システム全体も未完成です。**

## 比べる方法と判断基準

考案中に不足が見つかったとき、その場で新しい条件をカードの効果から検索できる入口が、案の発展と試す理由につながるかを調べます。検索補助そのものの採用は前の[実利用検証](../live-query-01/README.md)で確認しましたが、そこで候補は検索前にも読まれており、発見力の向上は示せていません。

今回はナイトメア・ローテーションの新規入力です。保存DBから選んだ全8記事URLを固定し、カード本文・双方の注記・記事・一般方針を同一版で渡しました。このクラスや全カードが初見という意味ではありません。開発者は具体カード・検索条件・期待する案を指定していません。

両方式の違いは、未提出の新しい条件を検索する操作とその案内です。検索の使用は強制しません。上限は考案20分、別評価10分を各一度。追加の自動改訂や、時間切れ後の考案やり直しはしません。既存の終了操作で、正式保存を確認してから次へ渡します。

検索回数や候補数を成果にせず、通常構築と同じ状態から比べて、どの不足が解決し、試す理由が残ったかを確認します。検索前から読んでいた候補や、評価者が後から足した手順も区別します。試用推薦・独自性・手順成立は別々に判断し、一回ずつの差で一般的な効果を断定しません。独自性の新しい問いが残る試用候補には、両方式で同じ条件の先例調査を一度接続する予定です。勝率・Tierは評価しません。

## 実施した手順と現在地

1. 探索条件と記事8URLを固定。初回の入力準備は、記事のレシピ読取りで約7.73秒後に中断しました。実AIはまだ起動していませんでした。
2. 8URL全部を点検。HTTPは全件200、7件は40枚照合まで成功、1件はレシピ表が最初の小見出しより前にあり読取り対象から外れていました。同じ保存原文の区切りだけを変え、失敗条件を切り分けました。初回失敗時の応答本文は未保存なので、当時の本文そのものを復元したとは扱いません。
3. 主節先頭の表を独立して読む修正を作成。複数レシピ表やコピー先を混ぜる場合の拒否も検査しました。既存68＋新規9、計77件と型検査が成功。保存8原文の修正前後比較は8件成功、既存7件の抽出保持でした。別担当も元失敗1件の主一覧16行・40枚と出力、コピー先、入替候補の非混入を照合しました。
4. 修正を本体へ反映して同じ8URLを再取得。約12.96秒で24資料を保存し、公開CLIからも読出しを確認しました。主DBは保持。両方式へ同じ修正を加え、旧実装・旧条件・失敗記録も保持しています。
5. 初回入力の一致と、案内以外の指示一致を実起動後にも照合。現在は両方式の考案中で、正式案・別評価の回収前です。

保存原文の照合では、GameWithの4件にそれぞれ5箇所の改行正規化がありました。原文バイトと読込み後の識別値を分け、両版へ同じ正規化後の文字列を渡した条件を追記しました。初回の独立照合での要訂正を保持し、追加の訂正確認も通っています。[正規化条件](intake-replay/normalization.json)と[別照合](intake-output-correction-check.json)を一緒に読みます。
