# 評価後の改訂と再評価を一度の実行でつなぐ

**改訂1件は保存できましたが、独立評価の保存に失敗し、実行補助としての採用を保留しました。** 別々に起動した担当が両方とも `/root` と名乗ったため、同一担当による評価と判定されて保存を拒否されました。実行は「評価未提出」で終了しています。

## 何を試したか

前の試行では、親担当が資料の複製、旧評価の分離、担当の起動、正式保存の回収を毎回個別に行っていました。今回、その受け渡しを一度のコマンドにまとめました。考案の指示と採否の基準は従来のままです。

保存案を固定 → 別の保存先で1回改訂 → 正式提出と入力保持の確認 → 新しい担当で1回評価 → 正式評価と報告の回収、の順に進みます。未提出や時間切れ、入力変更では停止し、自動再試行や代理提出はしません。

改訂担当には直前評価を渡し、次の評価担当には現在の案・カード本文・追加資料・改訂履歴を渡します。旧評価ファイルと古い考案資料は除きます。追加資料への旧採否の転記は、本文を別に点検します。

## 検証手順と結果

1. [条件](protocol.json)を固定しました。「経験参照あり・なし」の比較のB正式案と正式評価を使用し、改訂20分・評価15分、各1回としました。既知入力による実行工程の検査です。
2. 正常な引き渡し、未提出、期限停止、入力変更、余分な提出、評価資料への差し替えなどを検査しました。新規21件と関連する既存69件、計90件が12.66秒で合格し、型検査にも合格しました。合成回答の実プロセス検査を含みます。[検査範囲](verification.json)
3. 別担当の点検で見つかった、改訂履歴の欠落、余分な親評価の見逃し、親案を消した資料による形式だけの改訂を修正しました。[点検記録](independent-code-audit.json)
4. 実AIを起動し、9分12秒で改訂1件を正式保存しました。元資料の保持を照合した後、約0.6秒で別の評価担当へ自動で進みました。
5. 評価担当は5分43秒で終了しましたが、担当名の重複により公開入口での保存が1回拒否され、正式評価は0件でした。全体報告への正常な回収条件は満たしませんでした。[実行結果と時刻](live/verification.json)

事前テストは担当名を別々に用意していたため、実AIが同じ名前を返す問題を見逃していました。入力保全と未提出で止まる動作は確認できましたが、通常利用を最後まで通すという採用条件には不合格です。次は別々に起動した担当を実行側の識別値で区別し、正式改訂・別評価・全体報告までを再確認します。[修正の検証](../worker-identity-01/README.md)へ引き継ぎ、この失敗を成功へ変更しません。

## 案について分かったこと

改訂案「圧縮を外す潜伏ランプ：バトラーの強化をケイブへ」は、山札圧縮を撤回し、潜伏するフォロワーを強化して翌ターンの既存打点に重ねる方針へ変わりました。資料追加と構築方針の変更は確認できました。名称や検算だけの修正ではありません。

未登録の評価案には「条件付き成立・比較試用・独自性未確認」とあります。ただし、**この回答を正式な試行推薦や有用性の合格には数えません**。元の案・旧評価・今回の未提出を保持し、親担当による代理提出も行っていません。[未登録の最終回答](live/review/final-message.md)
