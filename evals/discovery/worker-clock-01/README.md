# 経過時計で作業時間を制限する選択肢

経過時計600秒で実AIを停止し、途中の資料を保持できました。一方、正式案は0件で、提出まで進める問題は解消していません。時間管理の動作と、提出・有用性の結果を分け、今回の方法の本採用は保留します。関連26件と型検査は合格です。

## 変更と理由

前の試行では、日時の差が約29分、経過時計は約13分の時点で、UTCの期限超過により停止したと読み取れます。時計差の原因は未確定です。同じ中断を繰り返さずに提出まで進めるかを見るため、`worker --clock elapsed` を追加しました。

既定の設定は、開始時に決めたUTC期限と経過時計の早い方で止まります。新しい選択肢は経過時計だけで制限し、開始・終了のUTC日時も記録します。経過時計は日付・時刻とは別の増加するカウンターです。待機を含み、CPU使用時間ではありません。OSにより休止の扱いが異なるため、実作業時間や絶対時刻の保証として扱いません。

担当と監視役へ同じ経過時計の期限を渡し、この選択肢では親から古いUTC期限を引き継がせません。停止条件の記録にも、どちらの時計が期限へ達したかを追加しました。

## 検証手順と現在位置

1. UTCだけを1時間進めた状況を模して同じ短い処理を比較。既定は期限停止、新しい設定は処理を完了しました。
2. 新しい設定の経過時間が上限へ達した場合は、途中の出力を残して停止しました。子処理の終了、入力拒否なども含め、既存20件と追加6件の計26件が合格しました。型検査も合格しました。
3. 中断したドラゴンの調査13資料を別の保存先へコピーし、元の資料との一致を確認しました。これは未知入力での再発見ではありません。
4. 実AIは9月10日06:21:38に開始し、07:23:48に期限停止しました。公開呼出し46回（ヘルプを含む）、失敗0回。公式検索の取得文を補助資料として1件追加しましたが、提案用JSONは未作成で正式案0件でした。
5. 正式案が無いため、案の独立評価は未実施で終了しました。元の17ファイルは一致し、増えた1資料を含む14資料を保持しています。

元の試行は正式案0件のまま[中断の記録](../fresh-reference-01/README.md)を保持します。固定した基準と旧入力は変更していません。新しい実行で案が出ても、前の試行の成功へ書き換えません。

## 日時と採否

実装の開始終了UTCは未記録です。検査の合格出力は26件・6.64秒で、これはテスト実行時間です。実AIの開始・終了と停止条件は[実行記録](completion/run.json)へ保存しました。日時差は1時間02分10.39秒、経過時計は10分00.07秒。停止判定の記録は経過600.001秒で、UTC期限による停止ではありません。原因不明の時計差は残っており、経過時計をCPU時間や実作業時間とは呼びません。

実AIは時間制限どおりに停止しましたが、提出・照合まで通すという検証条件は満たしませんでした。本採用は保留です。短い公開reportの読出しは約0.225秒で完了し、別担当も13資料・正式案0件・時計設定を照合しました。この成功を提案作成の成功へ転用しません。
