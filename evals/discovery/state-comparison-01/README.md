## 何を試したか

[前の改訂](../evidence-revision-01/README.md)は通常構築が同じターンにできる処理を過小に比較しました。今回は、通常側の手順を同じ開始状態と終点まで具体化する短い指示を加えると、案の判断が変わるかを試しました。

両側に同じ比較元の40枚を指定し、追加側だけに比較の手順を追記しています。現行側も比較対象の指定は受けるため、無指定の過去実行の再現ではありません。入力本体・19資料・旧案と旧評価・別評価の指示・回答形式は同一です。最新の失敗案・訂正箇所・期待するカードや手順は担当へ渡していません。

[固定条件](protocol.json)の5基準と、改訂15分・別評価10分、各担当1回の上限を維持しました。比較も15分の中に含めています。本体の既定指示は変更せず、隔離した実装で試しました。

## 検証した手順

1. 改訂前の保存資料を固定し、同じ比較元指定と追加側だけの短い追記を、隔離した2実装へ用意しました。
2. 新規入力を作る検査で共通文書の準備漏れが出たため、両側の検査環境を補完しました。関連62検査・型検査を通過し、公開入口で作った実入力が指示以外一致することを照合しました。
3. 両側を別プロセスで起動し、同じ改訂上限15分を適用しました。開始・終了は進捗記録へ自動反映しました。
4. 現行側は正常終了し、同じ評価指示による別担当の評価まで完了しました。追加側は正式保存後に期限停止し、評価未実施で打ち切りました。
5. 公開操作84件と正式保存内容を回収しました。公開操作の失敗は0件ですが、追加側の担当実行は期限停止しています。元の固定入力と本体DBは変わっていません。

途中報告でヘルプ表示を提出と誤認した親側の確認ミスが1回あり、その場で訂正しました。その後は正式な保存記録で件数を照合しています。実行側はヘルプを提出と認めておらず、この誤報で次工程を起動したり採点を変えたりしていません。[訂正記録](reporting-correction.json)を残しました。
