# 追加高速化の開発記録

追記: 最初の統合版 `a6dddc5` は暗号ライブラリ失敗時の問題を修正するため取り下げた。[再現・修正・再検証](crypto-fix.md)を参照。下の開発計測と `artifact-manifest.json` はその時点の証跡で、元のファイルは同コミットにも保存されている。修正版の確定ソース・証跡は `artifact-manifest.final.json`、総合判定は別のfresh担当による `../acceptance-final/` で確認する。

対象は、学習・評価用の「自分の現在の1ターン内に到達する全状態から、下位互換だけを除いた候補」の列挙。探索上限、盤面、候補の意味、抽選結果の扱いは変えていない。実装の候補選定に使った計測と、別担当による公開CLIの合否判定を分ける。

比較元は固定コミット `47eb2ef8d843dcc7c20d13f70a2a51eabf21a087`。以下は開発中の部分計測であり、足し算して最終CLI時間とはしない。全体の3回比較は独立受入レポートを参照する。JSON内の秒数・メモリは未丸めの生値。GB表記は10億bytes。

すべて同じ `independent-hard-cases.v1.json` の第1ケース。11,936,220状態、88,767,067結果、2,382,573候補。小さなケースや上限付きの未完了結果への置換はしていない。

探索10試行の生結果と各途中実装は [native/](native/README.md)。全状態とBFS到達手順のSHA256が、どの方式でも一致した。選択案の探索時RSSは約0.93GB、従来約2.07GB。候補比較では、全候補の**インデックスと順序を丸ごと照合**した。整形は全整数行と全候補の意味SHA256、保存は全ファイルSHA256を照合した。いずれも件数一致だけの判定ではない。

部分計測は機械語コンパイルを1状態で済ませてから測っている。全体受入では別プロセスの起動、キャッシュ読み込み、整形、ハッシュ、解放などを含め、保存時間も別記する。部分計測のRSSは各プロセスのWindows PeakWorkingSetSizeで、読み込んだ固定入力・初期化・照合も含む。異なる計測範囲のRSSを足さない。

## CPU使用量と並列化

試作の整形並列化では、プロセスCPU秒が1スレッド3.047、2スレッド3.734、4スレッド4.094だった。壁時計時間の短縮と引き換えにCPU消費は増える。最終版では131,072候補以上だけ最大4スレッド、それ未満は1スレッド。保持する作業はスレッド数分のバッチに制限し、元の順番に回収する。多数の学習ジョブを同時実行する側は `materialize(..., workers=1)` で照合の並列化を抑えられる。

SHA256はインストール済みPythonのOpenSSLまたはシステムの互換ライブラリを使う。対応シンボルが見つからなければ従来のPython処理へ戻る。キャッシュ済み機械語にプロセス固有のアドレスを埋めず、その都度関数を引数で渡す。新しいダウンロード・外部通信はない。

## 実測したメモリ確保

[旧版](allocations-predecessor.json)と[新版](allocations-delivered.json)を同じ `medium_4v4_order_split`、56,247状態、241,432結果で測定した。公開 `analyze_catalog` の探索＋候補比較に対し、Numba NRTカウンターとcProfileを有効化。ウォームアップを除いた**実際のNRT割り当て呼び出し回数は297,893→255**。同区間の解放回数もそれぞれ一致した。

これはNumbaのNRT allocation/MemInfo回数であり、bytes量・Python全体・OpenSSL等を含む全ネイティブ確保回数ではない。プロセス全体の割り当て総量は未計測。計測付きの0.096秒／0.071秒は順位決定に使わない。`.prof` にcProfileの生データも保持した。

## 再現コマンドとソース

作業ディレクトリはリポジトリroot、Pythonは `.venv/Scripts/python.exe -X utf8`。環境・依存版と最終ソースの確定は独立受入のmanifestにも記録する。途中の保存ソースは開発証跡で、本番モジュールではない。各保存ファイルのSHA256は `artifact-manifest.json`。

- 探索: `development/native/benchmark_native_variants.py` を各保存実装を入れた隔離checkoutで実行。実際のコマンド形式と計測区間は同スクリプト、採否はnative READMEに記載。
- 比較: `scripts/benchmark_skyline_max.py original output/turn-search-max/skyline/original.py`、続いて `single_get` / `fused` / `recycled`。原版以外は対応する保存実装を選んで実行。全状態配列・候補配列は `output/turn-search-max/export/*.npy`。生成は次のスクリプトが同じfixtureから行う。
- 整形: `scripts/benchmark_export_max.py final-materialization.json`。既存の出力名は上書きせず拒否する。
- 並列試作: `scripts/benchmark_parallel_export_max.py`。外側で1/2/4分割し、各分割のworker数を1に固定した比較。
- 保存: `scripts/benchmark_writer_max.py`。同一の保存済み行を両writerへ渡す。
- 確保回数: `scripts/profile_turn_allocations.py predecessor docs/evidence/turn-search-max/development/allocations-predecessor.json`。旧版は `PYTHONPATH=.../output/max-baseline-worktree/src`、新版はrootのsrc。別プロセスで同条件。

## 正確性・失敗履歴

`test`スキルに従い、正常系（全候補・意味ハッシュ・到達手順・確率）、境界（空、符号付き16/64bit境界、巨大整数への退避、衝突、索引拡張、同等代表、分岐順）、エラー（不正batch/worker数、ライブラリ不在、予算不足）を確認した。

- `.venv/Scripts/python.exe -X utf8 -m pytest tests/ -q -k 'battle or combat' --tb=short --disable-warnings`: **1,375 PASS、既存4 SKIP、無関係211 deselected、90.64秒**。
- strict mypy: native境界、export、export_native、io、skyline、変更した3テストの計8ファイル、PASS。
- native側の開発中エラーはnative READMEに保持。
- 辞書の`.get`戻り値はNumbaのOptional型となり配列添字へ使えず、コンパイルに失敗。型絞り込みの再試行でも同じ失敗が出たため、インストール済みNumba実装を読んで原因を確認し、整数演算で正規化して測定した。最終的には速度改善がなく案全体を外した。候補の契約は変更していない。
- 全テストの最初のコマンドで `-X utf8` を落とし、既存日本語fixtureがCP932で読まれて収集エラー3件。UTF-8を明示した上記実行で全件完了。製品の修正による回避ではない。

## 現在残る費用と限界

部分計測では依然として探索の約10秒が最大で、約8,877万結果に対する合法手生成・変更値更新・状態照合が残る。エンドポイント上の下位互換というだけで途中状態を消すと、能力や順序・抽選後の選択肢を落とし得るため、そこは省いていない。候補の整形と保存のPython逐次処理、遷移ごとの配列確保、汎用辞書の負担は大幅に減った。

追加キャッシュ・全キー索引・検索回数だけの削減には改善を観測できず、採用版を複雑にする根拠がなかった。有限の比較で絶対的な最速は証明できない。GPU、分散処理、操作交換可能性を証明して探索順を統合する方式は未検証。対応する効果の範囲、汎用処理へのフォールバック、1ターン内という範囲は従来どおり。
