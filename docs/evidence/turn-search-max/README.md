# ターン内候補列挙をさらに高速化

難しい5対5の2ケースで、計算時間の中央値を **46.75秒→19.27秒、31.14秒→12.56秒** に短縮しました。同じ全候補を出す条件で、合計約59%短縮、約2.45倍速です。過去に100秒台だった1ケース目は、今回19秒台まで下がりました。過去の数値は[前回の記録](../turn-search-speed/README.md)、今回の比較は新しく測り直した旧版を使っています。

| 5対5 | 計算時間・旧→新 | JSON保存・旧→新 | プロセス全体・旧→新 | ピークメモリ・旧→新 |
|---|---:|---:|---:|---:|
| ケース1 | **46.75→19.27秒** | 3.58→0.34秒 | 50.72→19.93秒 | **2.12→1.39GB** |
| ケース2 | **31.14→12.56秒** | 2.51→0.26秒 | 34.07→13.13秒 | **1.36→1.01GB** |

各版・各ケースを別プロセスで3回測定した中央値です。メモリは各試行のプロセス全体のWindows PeakWorkingSetSizeを十進GBで表記。計算時間は準備・キャッシュ読込・探索・候補比較・整形・SHA256・解放を含み、JSON保存は別列です。ケース1の新しい計算時間は19.154〜19.416秒、ケース2は12.466〜12.588秒でした。OSの時刻が無効な記録は採用せず、保存された単調時計の観測と照合しています。詳細な観測精度・限界は[独立比較表](acceptance-final/comparison.md)にあります。

1ケース目は11,936,220状態から2,382,573候補、2ケース目は8,661,088状態から1,643,067候補を得ました。両方とも上限に到達せず完了。全候補の整数行、重複、保存形式、初期状態とカード定義、代表的な到達手順は、新旧すべての試行と保存済みの過去出力で一致しました。これは大規模ケースの全件回帰照合であり、独立した全探索オラクルによる大規模証明とは区別しています。

主な変更は、行動で変わるフィールドだけの更新、全状態との比較を省略しない専用索引、消えた比較候補の領域の再利用、整形・照合・JSON保存の一括処理です。全192bitキーを索引に置く案や、検索位置を追加保持する案は、実測で改善せず外しました。[各方式の採否・生データ](development/README.md)を保存しています。

小規模9ケースは、独立オラクルと全状態・全候補・全行動の結果・正確な確率が一致しました。公開コマンドから42候補を復元し、42件の到達手順、抽選後に異なる手を選ぶ2分岐、上限時の未完了表示も確認しています。複合効果の2ケースは、従来どおり理由を明示して汎用処理へ切り替わり、完全な結果を返します。

関連テストは **1,379 PASS、既存の対象範囲限定4 SKIP**、型チェックもPASS。暗号ライブラリが存在してもSHA256を計算できない設定を実際に再現し、失敗時に正しいPython処理へ戻ることまで確認しました。[修正と再現](development/crypto-fix.md)を参照してください。

中規模3ケースの計算時間中央値も1.180→0.570秒、1.182→0.583秒、1.370→0.633秒に短縮しました。一方、汎用処理を使う小規模2ケースは1試行の観測で約2.3ms、5.2ms増え、少量のJSON保存も数ms増えています。小規模の値は単発の観測です。大きい出力の照合は最大4スレッドを使い、壁時計時間を短くする代わりにCPU消費が増えます。多くの学習ジョブを同時実行する場合、整形APIの `workers=1` で抑えられます。

起動・終了を含む時間では、最小の中規模ケースが1.536→2.041秒と増えました。全入力・全測定区間での一様な高速化ではありません。全試行の各区間と測定上の注意点は独立比較表に残しています。

現在の主な費用は探索です。最終ケース1の各工程の中央値は、探索11.81秒、候補比較4.44秒、整形・照合2.56秒。途中状態の無条件削除や上位数件への限定はしていません。機械語ランタイムの実際の確保回数も、同じ中規模局面で297,893→255回に減りました。これはNumba NRTの呼び出し回数で、全プロセスの割り当て総量ではありません。

有限のケース・このPCでの比較であり、絶対的な最速や全入力での一様な改善を証明するものではありません。GPU・分散処理・操作の交換可能性を証明して探索をさらにまとめる方式は未検証です。1ターン内、対応能力、汎用処理への切替という利用範囲は維持しています。

実測した旧版は `47eb2ef8d843dcc7c20d13f70a2a51eabf21a087`、新しい実装は `c178cae225e2cecc986fb88df2941391bd342c64`。入力・実行コマンド・実際のimport先・全試行は [独立受入の保存先](acceptance-final/) にあります。大きい候補JSONは `output/turn-search-max-acceptance-final/` に保持しています。

最終受入は **PASS**。[独立した最終比較](adjudication-v2/comparison.md)・[判定記録](adjudication-v2/report.json)・[仕様と報告の検査結果](adjudication-v2/lint.txt)に根拠を保存しました。新旧の全候補とランダム結果、到達手順、性能、上限時の表示、測定の再現性を確認しています。

最終受入の原実行では、全観測と監査が21分59秒、証拠の固定が23分11秒で終わり、事前に固定した60分枠内でした。ただし仕様v1の「native」という語が、指定するアルゴリズム名と実際の処理系を混同していたため、原判定は `INCOMPLETE / TEST_SPEC_ISSUE` のまま保存しています。実装や測定結果を見ていない別担当が公開契約を確認し、従来から汎用処理へ切り替わる指定2ケースだけを明確にした[仕様v2](spec.v2.json)を作成しました。速度・正確性・試行数・予算の条件は変えていません。745件の原データをハッシュで固定し、さらに別の担当がそれだけから再判定を完了しました。この訂正のための製品再実行・再計測は0件で、ソースと原データが変わっていないことも照合済みです。

再測定する場合は未使用の出力先を指定します。

```powershell
.venv/Scripts/python.exe -X utf8 -m svdeck.battle_frontier_compare --cases docs/evidence/turn-search-compare/independent-hard-cases.v1.json --algorithms native --trials 3 --max-states 100000000 --seconds 3600 --debug-threshold 0 --witness-samples 100 --output output/unused-max-check
```
