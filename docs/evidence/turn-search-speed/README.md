# ターン内候補列挙の追加高速化

前回のコンパイル方式をさらに短縮しました。5対5の計算時間は、今回同じ条件で測り直した前回版に対し **108.24秒→46.70秒、68.07秒→29.44秒** です。候補集合・保存形式・確率・条件付きの操作選択は維持し、同じ計算の繰り返しを減らしました。

| 5対5ケース | 版 | 計算時間 | JSON保存 | プロセス全体 | 最大常駐メモリ |
|---|---|---:|---:|---:|---:|
| 1 | 前回版・再測定 | 108.24秒 | 3.51秒 | 112.10秒 | 2.43GB |
| 1 | 改良版 | **46.70秒** | 3.70秒 | **50.77秒** | **2.12GB** |
| 2 | 前回版・再測定 | 68.07秒 | 2.55秒 | 70.96秒 | 1.54GB |
| 2 | 改良版 | **29.44秒** | 2.55秒 | **32.33秒** | **1.36GB** |

両ケースとも全件完了し、計算時間は合計で約57%短縮しました。メモリはOS計測のプロセス最大常駐量、十進GBです。1件目は11,936,220状態・2,382,573候補、2件目は8,661,088状態・1,643,067候補です。大規模は各版各1試行なので、繰り返しのばらつきや別PCでの速度まで保証する結果ではありません。

1件目の内訳は、探索26.76秒→26.29秒、候補整理36.11秒→5.22秒、出力用データ化・照合44.11秒→13.97秒でした。主な改善は後ろ二つの処理です。中規模3ケース各3試行では、最小ケースの中央値が1.1127秒→1.1293秒と約1.5%増え、中規模の最大常駐量も約1.5〜6.3%増えています。全入力で一様に改善するという主張ではありません。[全試行と比較表](acceptance-v2/comparison.md)を参照してください。

- 探索中、状態数上限の検査で得た「未登録か」の判定を、その直後の追加にも再利用します。ランダムの全出目が上限内に収まることを確認してから追加する規則は同じです。
- 候補整理では、スタッツや資源の比較値を一度だけ作って共有し、複数項目を一括比較します。数値が範囲外なら従来と同じ整数比較へ戻します。攻撃と体力、残手札などの優劣が決まらない候補は残します。
- 出力時はカード能力・盤面形状の共通部分を再利用し、変わる数値をまとめて変換します。従来と同じ整数行、同じSHA256照合値を出します。

入力 → 全到達状態の列挙 → 厳密な候補整理 → 同じ形式の候補JSON、という処理です。到達状態の削減や時間上限による打ち切りを高速化として数えていません。学習用のメモリ内APIにも探索と候補整理の改善が適用されます。

改良版を再測定するコマンド（保存先は未使用の名前にします）:

```powershell
.venv/Scripts/python.exe -X utf8 -m svdeck.battle_frontier_compare --cases docs/evidence/turn-search-compare/independent-hard-cases.v1.json --algorithms native --trials 1 --max-states 100000000 --seconds 3600 --debug-threshold 0 --witness-samples 100 --output output/unused-speed-check
```

全候補を毎回JSONへ保存しない学習ループでは、[既存の `analyze_catalog` API](../../battle-frontier.md)も使えます。

[自動検証](validation.json)は1,367 PASS、既存の対象範囲限定4件がSKIPです。追加テストでは生成96ケースの全到達状態、比較値の境界1,000組、同値・支配・大小不明の候補が到着する全120順序を確認しました。

開発時に出力処理だけを変えた2件目は47.08秒、出力用データ化と照合は8.87秒でした。これは最終実装の測定ではありません。[開発観測](development/notes.md)と[生データ](development/export-only-hard2.json)を残しています。最終比較では前回版を別の作業ディレクトリから動かし、同じ入力・同じ候補出力で新しく測定しました。

独立検証は[固定仕様v2](spec.v2.json)で **PASS、機能・利用上の指摘0件** でした。[最終報告](acceptance-v2/report.json)に根拠を保存しています。小9ケースの全状態・候補・操作・確率を独立oracleと比較し、42候補の公開入口からの復元、抽選後の条件付き操作、上限による未完了表示も確認しました。中規模・大規模の新旧・過去33出力は、埋め込まれた初期状態・カード定義と、重複を含む全候補の整数行が一致しています。製品が出した照合値だけを信用する検査ではありません。

v1には公開CLIから指定できない試行順と、公開されていない復号仕様を要する検査があったため、大規模測定の前に別担当が訂正しました。候補・確率の正確さ、測定回数、完全列挙、前回版より速いという条件は維持しています。v1の未完了記録は[そのまま保存](acceptance/report.v1.json)し、v2は新しい担当が小ケースから実行しました。
