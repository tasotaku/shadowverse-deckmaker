# 対戦AI：方式と検証

対戦ラボの「AIが一手実行」で、今の局面からAIに手を選ばせます。「自動対戦」は両者の手を同じ方式で選びます。
「AI対戦例を開く」は終局まで実行済みの記録です。一手ずつ進む・戻る・ターン移動に対応し、
右の「この手のAI判断」で理由と比較候補を確認できます。保存記録にも判断を残します。
演出OFFにすると表示待ちを省略します。

## 選んだ構成

現在の標準は判断方式2です。相手の返しを読む判断方式3は比較用の試作として追加しています。
共通の盤面評価と現在ターン内の手順探索を組み合わせます。カード名ごとの手順表は作らず、
対戦処理に合法手を実行させて、体力・盤面・能力・手札枚数・PP最大値・進化権・危険を比較します。
勝敗は通常の評価より優先します。両デッキに同じ方式を使い、デッキ別の結果も分けて測定します。

| 方式 | 役割 |
|---|---|
| 無作為 | 最低限の比較対象。合法手から選ぶ |
| 一手評価 | 1手後だけを比較する固定基準 |
| 先読みAI | 最大6手、各段階で上位6経路、最大160候補を試す |
| 調整した先読みAI | 対戦結果から11個の評価重みを変え、同じ探索量で比較する |

深いニューラルネットワークによる強化学習は今回実装していません。小さな評価式の重みを変え、
対戦で勝ちやすい候補を残す進化的な学習を実装しました。逐次LLMも呼びません。
今ある環境で高速・再現可能に比較でき、弱い判断を手順と数値で調べられる構成を選んだためです。
LLM方式や深層強化学習より強いと実験で示したわけではありません。

参考にした研究は、[Hearthstoneの評価方式を対戦から調整する研究](https://arxiv.org/abs/2410.19681)と、
[学習した盤面評価を探索に組み合わせる研究](https://arxiv.org/abs/1808.04794)です。
これらは方式選定の参考であり、本実装が論文の手法・性能を再現したという意味ではありません。

## 覗き見を防ぐ境界

`Player.choose()` に渡すのは `Battle.observation()` の出力と公開カード定義だけです。
実際の相手手札、両山札の中身・順番、内部乱数、次の個体番号は渡しません。
画面で両者の手札を表示してもAIの入力は変わりません。

探索用には枚数を維持した仮の手札・山札を作ります。公開済みカードのクラスを参考に登録カードから仮定する簡易方式で、
正確な残り枚数の推定や既使用カードの記憶は未実装です。独立した2通りの仮定を使います。
ドロー・デッキからの召喚・ランダム処理に触れたらその経路の先読みを止め、実行後の新しい観測で考え直します。
確定した勝ちとして表示するのは、未知の結果を含まない手順だけです。候補の評価値は勝率ではありません。

生成カードの番号は仮想盤面と実際の盤面で異なります。画面の対戦は毎回一手を選び直し、
`execute_plan()` は生成後の公開位置とカード種から仮番号を解決して、決定的な手順を実行します。
未知の結果を含む手順はまとめて実行せず拒否します。

## 測定方法

- 初手の引き直しは両者ともなし。登録済み2デッキの同種対戦2組と異種対戦1組で比較。
- 各開始条件でAIの先後を入れ替える。デッキ配置・初期乱数・探索上限を固定する。
- 学習は101〜112（1手評価の重み）、301〜312（先読みの重み）。評価用の乱数とは分離。
- 勝ち1点、引き分け0.5点。500操作で未終局なら別件数として記録し、勝利や引き分けに混ぜない。
- 全試合の先後・デッキ・勝敗・操作数・計算量・所要時間をJSONに保存する。
- 勝率の区間は同じ条件の先後ペアを再抽出した参考値。小標本や全勝の場合の確実性を保証しない。
- 最終評価を見て重みを再調整しない。比較相手と条件に対する相対性能であり、人間上級者との比較ではない。

## 再実行

```sh
# 一手評価の重みを学習（結果を直接採用はしない）
.venv/bin/python -m svdeck.battle_training train --output training.json --workers 4
# 同じ計算量の先読みAIを対戦で調整
.venv/bin/python -m svdeck.battle_training train --training-policy search --output search-training.json --workers 4
# 未学習条件で比較
.venv/bin/python -m svdeck.battle_training evaluate --policy search --opponent greedy --seed 10001 --seeds 16 --output evaluation.json
# 人が見返せる一試合を保存
.venv/bin/python -m svdeck.battle_training replay --policy search --opponent search --seed 24051 --output replay.json
```

`train` に `--model-output candidate.json` を加えると小さな重みファイルも保存します。
プログラムからは `Player(cards, weights=model['weights'])` でその候補を比較できます。
配布モデルを差し替える前に、別の開始条件と戦術課題で検査します。

保存したリプレイは対戦ラボの「記録を開く」で読めます。画面は通常の `svdeck-battle-web` と同じ8767番です。
`battle_ai.py` が判断、`battle_training.py` が学習・測定を担当し、効果処理や演出とは分離しています。

## 残る弱点

現在ターンを中心に限られた候補だけを探索します。相手が次に手札から使うカードを含む長期の読みは行わず、
相手の盤面から受ける危険も評価式による近似です。ドローを挟む長いコンボ、手札の温存、構築全体の勝ち筋、
初手交換の最適化は弱点として残ります。環境のルール再現に誤りがあれば、その誤りを利用するAIにもなり得ます。
今回の成績は自作環境と収録2デッキの範囲の結果です。

ゾーイを倒せない2/1の突進攻撃が、何もせずターンを終えるより高く評価される原因の一つです。

相手の手札からの反撃や対面全体の長期有利はまだ読めません。カード名を条件にした指示は加えていません。

## 相手の返しを読む（2026-09-14、判断方式3）

ユーザーの指摘を受け、試作の `reply` は既知の構築から仮定した相手手札で、実際に相手の行動を試します。
自分のターンを中心に読む方式2は標準の `search`（別名 `turn`）として維持します。逐次LLM・ニューラルネットワークは使用していません。

1. 自分の現在ターンの手順を最大160候補まで試し、返しを検査する手順を最大8つ残す。
2. 公開デッキの採用枚数から、公開済みの元カードを除き、相手の手札と山札を8通り仮定する。
3. こちらの同じ手順を8通りすべてに適用し、相手がその手札・PPでできる返しを試す。
4. 各手札で自分の評価が最も悪くなる返しを取り、その8通りの平均が最もよい手順を選ぶ。
5. 実際には最初の一手を実行してから、観測し直して考える。

先読みの終点は「自分の残りターン→相手の返し→次の自分のターン開始」です。
相手の探索は各手札・各候補につき最大64行動、最大6アクション、各段階で上位3経路です。
採用候補にはパスと、同じ初手から追加の手札を使わず止める経路も含めます。
自分の候補生成に既存の評価式を使うため、そこで落とした手順は返しまで読めません。
表示する「試した手」には相手の候補も含みますが、採点のためのターン終了処理回数は含みません。

### 手札の仮定と情報の境界

各構築は初期の40枚の**カード別枚数だけ**を既知として登録します。本物の手札・山札順・乱数はAIに渡しません。
公開した元カードは物理的な1枚として一度だけ差し引き、手札戻しで番号が変わっても二重に減らしません。
生成コピーやトークンは元デッキの消費として扱わず、公開済みの生成・戻り手札は既知の手札として置きます。
手札・山札は残りから重複なしで抽出するので、必要な3枚は3枚とも引いた仮定でだけ使えます。

例えば残り9枚に特定の3種が各1枚、非公開手札3枚なら、特定1枚を持つ確率は1/3、
特定3枚すべては1/84です。これは均等抽出という仮定での数値です。
実戦で特定カードを温存しやすい傾向、引き直し方針、過去に使わなかったという情報からの推定は未実装です。
8通りでは珍しい返しを見逃すことがあります。表示する敗北サンプル数は実際の勝率ではありません。

自分の手順は隠れた手札ごとに変えません。相手の返しの採点もこちらの実際の手札内容を参照しません。
途中で未知のドローやランダム結果を挟む経路はそこで打ち切り、終了時点までの結果を近似評価します。
相手手札の仮定から「確定勝ち」とは認定しません。公開情報だけで現在ターン中に勝てる従来の検査は維持します。

古い保存対戦でも未使用の初期40枚が残っていれば、現在の再生位置までの操作だけで知識を再構成してAIへ渡します。
元の保存状態・未来のフレームは書き換えません。初期構築がない自由配置の局面では方式2相当へ戻り、
相手手札の返しが未探索であることを判断理由に表示します。

### 能力の扱いと限界

バリア・必殺・ドレイン・破壊耐性の戦闘、ラストワード、ターン終了時能力は、
探索中に発動した分を対戦エンジンで実処理します。同じ4/4でも全除去後に後続を残す札と、
体力満タンで小回復だけの札を区別する固定課題では、従来方式が小回復を選び、新方式が後続を残す札を選びました。

**終点の評価式は近似のままです。** 読んだ範囲で発動しない能力の価値には以前の粗い加点が残ります。
デッキごとの長期有利や最適な体力の使い方が解けたわけではありません。
本手法は手札を仮定した有限の応答探索で、完全な最善応答・厳密な勝率・ISMCTSの実装とは呼びません。
隠れた状態を仮定した探索の限界は、[Cowlingらの原論文](https://eprints.whiterose.ac.uk/id/eprint/75048/1/CowlingPowleyWhitehouse2012.pdf)も参照しました。

判断記録の `response_search` に各候補の平均・最低評価、8通りの得点、最悪だった仮定の手札・必要札・返し手順を残します。
画面の判断理由にも平均・最低評価・敗北サンプル数を表示し、「仮定した相手の返し」を開くとカード名つきの手順を読めます。
新方式同士の[一試合のリプレイ](evidence/ai-reply-search-replay.json)は乱数40001、48操作で終局し、保存再生の一致を確認しました。

### 比較結果と採否

初回比較（乱数41001〜41004）は24戦10勝14敗。公開済み手札のコスト変更の反映を修正した後の
別条件42001〜42004でも、**24戦10勝14敗、引分・未終局0**でした。
後者の参考区間は25.0〜58.3%、ドラゴン4/12勝・ナイトメア6/12勝です。
前後とも同種2組と異種1組、先後入替。結果を見て重みを再調整していません。
[初回](evidence/ai-reply-vs-turn.json)・[修正後](evidence/ai-reply-vs-search-final.json)に全試合を保持しています。
初回と一試合リプレイは開発中の一時的な `search` 名で方式3を実行した記録であり、
当時のラベルを維持して現在の相当方式を注記しています。

既知の対戦例の先攻3ターンでルリアを選び、先攻4ターンでも顔を攻撃する判断が再発しました。
返しまで読むことだけで、候補を落とす問題・終点の粗い評価が解消するわけではありません。
このため**方式3は標準に採用せず、画面の「相手の返しを読む（試作）」で選択する比較用**です。
従来方式の指摘4局面の検査も維持しています。相手の手札が既知の場合と異なり、
仮定手札を増やすほど計算が重くなり、利用画面でも一手約3.6秒の局面がありました（並列対戦測定と同時実行）。

検証は対戦関連272テストと静的型チェックPASS。カード枚数・非公開情報・戻り札/生成札・公開済み手札のコスト変化、
能力内容による判断差、必要PP、同時に揃う手札の頻度、旧リプレイからのAI実行を含みます。
利用中の `http://127.0.0.1:8767/` で試作選択→一手実行→仮定の返し表示を確認しました。
[判断理由](evidence/battle-reply-reason.jpg)・[相手の返し](evidence/battle-reply-ui.jpg)の独立画像確認は4項目PASSです。
同じURLの[実応答](evidence/ai-reply-live-check.json)には、標準で啓示・バット処理を維持することと、
試作ではルリア展開・顔攻撃を再選択することを併記し、採用しなかった理由を追えるようにしています。

## 能力なしの盤面候補（2026-09-14）

「攻撃のみ」「進化まで」「超進化まで」の3範囲で、今のターンに実行できる操作列を生成する
`battle_combat.analyze()` を追加した。LLMへの問い合わせや途中状態の加点は使わない。
通常の対戦AIにはまだ組み込んでいない。カード能力を戻した際に安全な候補削減かは別に検証する。

### 利用と適用範囲

対戦ラボの **「盤面の候補」→「調べる」→候補の「手順を再生」** で利用できる。
既存の「一手進む」「一手戻る」で再生し、「元の対戦へ戻る」で元の履歴・再生位置へ復帰する。
候補番号は強さの順位ではなく、顔への打点順の表示である。
検証中は能力なしの別状態を表示し、通常AI・カード使用は無効。再読み込みでは元の対戦を復元する。

現在の攻撃力・現在/最大体力・進化状態・攻撃済みか・今ターン登場したかと、EP/SEPを引き継ぐ。
カード使用、すべてのキーワード、固有能力、アミュレット、クレスト、リーダー効果を除く。
基本の進化・超進化は[公式の対戦ルール](https://shadowverse-wb.com/ja/system/cardbattle/battle/)に沿って残す。
具体的には通常+2/+2、超進化+3/+3、手番側の超進化のダメージ無効と戦闘破壊時の顔1点、
先後の解禁ターン・一ターン一回・攻撃済みを解除しない制約を含む。
「攻撃のみ」でも、既に超進化している個体の基本効果は残る。
終了候補とは**ここで攻撃を止める状態**。ターン終了処理・次のドローまでは進めない。

### 候補を落とす条件

1. 合法な攻撃・進化をすべて生成し、途中の点数で上位件数に絞らない。
2. 両盤面の各個体の数値・進化状態・残り攻撃権・顔への攻撃可否、顔体力、EP/SEP、
   今ターンの進化使用済みかが同じ局面を統合する。能力なしでは個体の名前や左右位置に意味がないため、
   同じ状態の個体を入れ替えただけの経路も統合する。再生には実際の個体IDを持つ代表経路を保存する。
3. 探索したすべての状態を「ここで止める」候補にし、終了状態の重複を除く。
4. AがBより顔打点・残りEP・残りSEPで劣らず、Bの味方全員をAの別々の味方に対応させて
   攻撃力・現在体力・最大体力がそれぞれ同等以上、かつAの敵全員をBの別々の敵に対応させて
   同等以下なら、Bを除く。対応する個体は同じ進化状態であることが必要。
   一体を複数体の代わりに数えず、大型一体と横展開を合計値だけで比較しない。
   同じ勝利に至る候補は代表一件を返す。

手順2の統合はこの限定モデルの同一性に基づく。手順4は**指定した終了状態の比較基準における優劣**であり、
相手の将来のカードや、相手の超進化で破壊される的の有無まで含めた戦略上の優劣ではない。
総攻撃力等を使って「明確な下位互換」と断定したり、この比較を途中の枝刈りへ転用したりしない。
比較を高速化する集合演算は必要条件の判定に使い、最後は個体の対応を厳密に検査する。

画面は50,000状態を上限とする。未探索の枝があると `complete=false` を返し、
「探索上限で打切り・未探索の候補があります」と表示する。その場合、返す候補が後の探索で
劣位と判明することもある。ページ分けは候補を削らず、全件を閲覧できる。
Pythonから `max_states=None` を渡せば状態件数の上限なしで完全列挙する。大きい局面の時間・メモリは保証しない。

```python
from svdeck.battle import replay
from svdeck.battle_combat import analyze

battle = replay(record, cursor=30)
result = analyze(battle, mode='super', max_states=None)
candidate = result['candidates'][0]
witness = replay({**result['record'], 'actions': candidate['actions'], 'frames': []})
```

HTTPは `POST /api/combat` に `{record, cursor, mode}` を送る。結果には能力なしの初期記録、
候補ごとの操作列・両盤面・相手体力・EP/SEP、探索状態数・統合数・比較で除いた件数・所要時間を含む。

### 確認結果

- 小さい盤面12条件×3モードについて、既存エンジンで**状態を統合せず全操作列を列挙**した結果と、
  終了状態の集合・除外後の候補を照合。独立した対応付けの総当たりを正解側に用いた。
- 出力した候補は個体ID付きの操作列を既存エンジンで再実行し、候補の終了状態と一致。
  進化解禁、召喚したターンの攻撃制限、超進化の顔1点、攻撃後の進化、複数体の犠牲による処理、
  EP/SEPの選択、同数値の個体の統合、不正入力・探索上限を検査した。
- 対戦関連 **294テストPASS**。mypy・JavaScript構文検査PASS。
- 利用中の `http://127.0.0.1:8767/` から15条件を実行。既存リプレイ30手目は、
  攻撃のみ5候補、進化あり13候補で完全探索。探索部分は約0.6〜1.5ms（通信・元記録の再生・描画は除外）。
  [実応答](evidence/combat-live-api.json)に保存した。
- [計測用盤面と結果](evidence/combat-benchmark.json)：同じ2/3が双方に5体は279状態・44候補、約17msで完了。
  数値が異なる5対5の2例は5万状態で打切り、約4.1秒/4.5秒、5,936/4,232候補。
  完全探索の時間や対戦AI全体の高速化を示す測定ではない。
