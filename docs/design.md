# 設計: 想定外デッキの「種」提案システム

2026-07-05 ロック。以降の実装はこの設計に従う。変更するときはこのdocを先に直す。

## 1. 目的とゴール

**「独自で、そこそこ戦えるデッキ」の種を提案する**支援システム。

- **想定外の定義**: 基準は運営の意図ではなく、その使い方が「**一般に広まっているか**」（§7）。
  誰かが試しただけで候補から除外しない。運営想定外でも既に流行していれば独自性の根拠にはならない。
  逆に、運営想定内の弱いアーキタイプが1枚差しで化けるケースも本命。2026-09-10に、冒頭の表現を
  2026-07-05確定の§7へ揃えた。既存の判定基準と過去の採点は変更しない。
- **強さの要件**: tier3程度（環境デッキに勝率は低いが戦える）で合格。2026-09-06のユーザー補足では、
  マゼルテンポエルフのようにtier3〜4程度でも、独自性と初見での対処の難しさによって上位と戦えるなら目指す価値がある。
  tierや初見での優位はユーザーの実戦評価として扱い、未知の構築へ勝率の加点として自動転用しない。
- **出力の粒度**: 40枚デッキは組まない（AIは実プレイで検証できず強さを保証できない）。
  出力は**デッキの種** = 核カード数枚 + 想定クラス + なぜ噛み合うか + 想定の勝ち筋 +
  新規性の根拠。40枚化と実戦検証は人間の仕事。
- **非対象**: 対戦シミュレータ、勝率予測、デッキの完成。

### 1.1 開発の責務（2026-09-08・ユーザー訂正）

この作業の対象は**デッキを探索するシステムの構築**であり、開発者自身による個別のデッキ探索ではない。
カードを調べる実験は、実装した工程が有用かを確かめ、失敗原因を実装へ戻すために行う。
調査報告の保存、候補の提案・棄却、手順の文章化だけで開発を一区切りにしない。
公開された入口から実行できる工程を実装し、過去の成功例・失敗例と新しい入力で評価・修正を続ける。
テスト合格や説明項目の充足だけを完成の根拠にせず、ユーザーの望む種へ進める有用性を示す。
ユーザーは、よいシステムが完成するまで継続して作業することを明示的に依頼している。

## 1.5 フォーマット公理（2026-07-05・3周目のユーザー訂正で追加。全工程に先立つ前提）

**ゲームルール・用語の正準は docs/rules.md**（公式キーワード定義はDB `ability_keyword` テーブル）。
本docにはパイプライン運用に直結する帰結だけを書く。

フォーマットのルール自体は rules.md#フォーマット。パイプラインへの帰結:

- **種・クロージャは必ずフォーマットを明示**し、クロージャ内全カードが同一フォーマットで合法である
  こと（クラス整合と同格の必須制約。合法性は `card.is_include_rotation`）
- **novelty壁もフォーマット別**。「ローテのデッキに入っていない」はローテ落ちカードには無意味
  （合法性の帰結であって未踏の証拠ではない）。meta_deck はローテ+アンリミのTier表を収集済み（2026-07-05〜）
- アンリミの種も対象。ただし相対的に高いカードパワーが要求されるため、④目利きでは強さの閾値を一段厳しく見る

## 2. データソースの信頼度階層

| ソース | 役割 | 信頼度 |
|---|---|---|
| 大会入賞デッキ（shadowverse-magazine / RAGE / OCS。月〜季節ごと・入賞レシピと使用分布が公開） | 環境把握 + 既知の壁（強） | 高・実績 |
| gamewith / game8 のTier表 | 環境把握 + 既知の壁（弱） | 中・参考程度（諸説あり） |
| 公式Deck Portal 全投稿デッキ | **共起オラクル**（人類が試したペアの母集団。品質は不問） | 品質判定には使わない |
| JCG（WBでは開催確認できず）・アルテマ・非公式wiki 等 | 不採用 | — |

Deck Portalは誰でも投稿できゴミも多い＝メタ把握には使えないが、「この組み合わせを
誰かが試したか」を数えるには完全網羅が好都合、という使い分け。

## 3. パイプライン全体図

```
[カードDB 826枚]
   │ ①抽出: 能力→型付きアトム（LLM・カード1枚1回・キャッシュ）
   ▼
[アトムDB]──アンカー選定（ヘッドルーム大のみ・人が確定）
   │ ②マッチ: 要求コンパイル→逆引き索引→算術チェック→クロージャ組み
   ▼
[候補クロージャ（アンカー+供給セット）]
   │ ③novelty: 共起オラクル＋大会/Tierの壁でフィルタ
   ▼
[未踏候補]
   │ ④目利き: LLMがconcept-levelで出オチだけ足切り（強さの保証はしない）
   ▼
[種の上位]
   │ ⑤言語化: 人間がすぐ試せる形で出力
   ▼
[人間: 40枚化・実戦検証]
```

LLMを使うのは①④⑤と②の想起補助（LLM走査・§6.1）のみ。**判定（集合演算＋算術）は機械**で
型一致に閉じる。広く安く削り、狭くなってから高い道具を使う。

### 3.1 利用モード（2026-07-05追加）

- **対話クエリモード（主・v1はここから作る）**: 人が「このカードをこう使えたら強いはず。
  ◯◯できるカードはないか」と聞く → 要求にコンパイル → 逆引き索引＋算術チェックで候補提示。
  アンカー選定とnoveltyを人の直感で代替する軽量経路。
- **自動探索モード（従）**: ②〜⑤の一括列挙。対話モードで索引とマッチの質が枯れてから回す。

### 3.2 発想を発展させる入口の実装（2026-09-08・試作）

`python -m svdeck.discovery` を、AIが資料を読み、仮説を提出し、その不足を検索へ戻す入口として作る。
既存の `explore` は条件から候補を引く下位の道具として残す。この試作の実装をもって方式の本採用とはしない。

- 探索開始時にフォーマットと対象クラスを固定し、DBから本文・進化・参照先・関連カード・両側の注記・要求・既知デッキを保存する。
  全文資料はその都度作り、別生成の古いメモに依存しない。出典時点と資料の識別値を残す。
- 全文を一度に表示できない場合は `packet --summary` で保存資料の識別値・指示・回答例・区分ごとの件数を得る。
  `read SESSION PACKET_HASH SECTION` はその保存版だけを読み、カードは枚数、長い文章は行数で分割する。
  総数と次の読出し位置を返し、分割しても元の全文資料の識別値を保持する。読出し中に資料を再生成しない。
  概要の区分一覧には全文JSON内の参照位置も示し、カード・ルールが `data.context` 内にあることを操作時に確認できるようにする。
- 最初の問いは特定アンカーを必須にしない。役割の読み替え、効果の副作用、複数段の接続、強い基盤と採用配分を検討できる。
  仮説は親の改訂を指定して追記する。新しく生じた条件を次の問いにし、タグ検索と全文走査へ戻す。
  同じ案の説明を増やすだけの改訂を推奨せず、何を変えたか・何が解決したかを残す。
- `attach` は比較資料・観察を、出典・時点・本文・限界とともに追記する。既存の資料版や評価は変えない。
  新しい資料では出典の識別値と正確な引用を照合できるが、内容の真偽や主張を支えるかまで機械で認定しない。
  `attach-file` は、指定したUTF-8ファイルを本文としてそのまま取り込み、表題・種類・出典・観察時点・限界を別に指定する。
  JSONの報告も文字列の本文として保存し、項目の書換えや成功判定は行わない。入力ファイルの識別値を返し、古い入力・案・評価は変えない。
  ファイル保存の確認は探索方法の有用性と区別する。
  `history` は選んだ枝の先祖案、提出時の検索、資料の識別値を渡す。別評価には過去の評価記録を混ぜない。
  検索で見つからなかったことと全範囲で不可能と確かめたことは別なので、実施した検査結果も資料として残す。
- `report` と新しい改訂用資料には、各評価の識別値・入力資料版・その版の追加資料一覧・現在との差分・残った問いを
  `review_contexts` として添える。評価の入力資料版を辿って照合し、不整合や参照先の欠落では出力を中止する。
  差分はその入力版に含まれない資料であり、担当が実際に読んだことや評価提出後に追加されたことの証明ではない。
  同じ資料版に対する異なる評価も残し、資料件数・新旧・並び順から評価の正しさや最終判断を決めない。
  古い問いは資料追加だけで解決済みにせず、既存の再検索も変えない。別評価用資料には過去評価のこの情報を渡さない。
  分割読出しは保存版の対応情報を返し、旧版に項目がなければ空配列と欠落した参照位置を示す。資料機能以前の入力は資料0件として扱う。
- `compare` は追加資料の全40枚リスト2件から、実際の追加・除去札と総数、種類・コストの分布を計算して資料に残す。
  種類の純増減と交換総数を分け、部分内訳から全リストを補完しない。元資料2件と保存DBの識別値を保持する。
  当時の能力・合法性を復元する機能ではなく、交換の強さを算術から認定しない。
- `meta --article URL --format FORMAT` を、必要な公開記事だけを取得する入口として追加する（2026-09-10・資料取得補助として採用）。
  全件取得が5分で完了せず、初期資料には7月取得の参考構築が残っていたため、比較に必要な記事を直接指定できるようにする。
  カードDBは読み取り専用とし、既存の解析と40枚検査を使う。複数構築は分け、40枚の内訳と記事更新日時・取得対象・表示表との不一致を資料として出力する。
  出力は既存の `discovery attach` で取り込み、`compare` へ渡す。元の固定入力や既存の環境デッキ一覧は変更しない。
  現在のTierや当時の能力は記事取得から補完しない。これは資料取得の改善であり、発見力の改善とは別に検証する。
- 未完成の着想を提出できる。条件の未解決、手順の検証、試す価値、既出調査は別に扱い、
  項目を埋めただけで「強い」「新しい」へ昇格させない。手順と構築の比較判断は根拠付きの別評価として取り込む。
  回答例は外部調査記録の項目名も示す。調査していない場合は空配列とし、形式の補足によって実施を装わせない。
- `packet --finish-from-source HASH` は、保存済みの調査を提案へまとめる担当への任意の引き継ぎ（2026-09-10・試作）。
  指定した資料が同じ探索内に存在することを確認し、その識別値と専用の指示を入力版へ保存する。
  指定資料→作業用JSONの先行保存→必要な本文・注記・不足の確認→既存の提出・レポート、という順で進める。
  通常の考案指示、資料の全文、提出検査、別評価の基準は維持する。下書きの存在を正式提出や有用性と数えない。
  資料内の着想は未評価のデータであり、誤りを引き継いで正当化しない。新資料を追加したら、同じ指定で新しい入力版を作る。
  新規探索に短い着想を先行保存する旧比較とは分け、調査済み14資料から提出・独立評価へ進めるかを別に検証する。
  実利用は正式案1件・独立評価1件まで完了したが、試行推薦0件で本採用保留。任意の入口の動作確認と探索方法の有用性を分ける。
  採用利益が基準構築の不足を解消する根拠と、引用した本人記事の不採用理由の扱いが課題として残った。
- 実際の保留案と別評価から、採用負担を減らす配分・使い方の変更を優先する改訂指示を隔離して比較（2026-09-10）。
  通常の改訂入力だけを変え、初回考案・独立評価・資料引き継ぎ・回答形式は維持する。既知入力の再利用として記録し、
  前試行を再採点しない。改訂や資料が増えたことと有用な種への到達を分ける。
  改訂は両方式で提出済み。独立評価は利用上限で未完となり、同じ入力で新しい評価を別試行として実施。
  復旧後は両案とも試行推薦に進んだが、同数のため指示変更の上乗せは未立証。本採用は保留。
  固定条件と進捗は [採用負担を減らす改訂の比較](../evals/discovery/burden-revision-01/README.md) に保存する。
- 効果の原文解釈まで算術で証明したことにはしない。機械は資料内のカードID、合法性、クラス、改訂と証拠の対応などを検査する。
  初版は対戦シミュレータを作らず、PP・盤面・手札・進化権・相手依存を時系列で別評価する。
- 従来入口の「全要求を閉じた集合」は未充足要求を除外して返さない。量だけの楽観概算をPP収支PASSと呼ばず、
  型一致・数量の概算・手順の成立を出力で区別する。環境デッキの同居照合はフォーマット別に行う。

- `recall LIBRARY --card-id ID / --query 語` は、別探索の正式案・評価をカードと使い方から読む入口（2026-09-10・検索補助として採用）。
  役割にある全指定カードIDと、案・計画・未確認・評価理由の全検索語を照合する。資料全体のカード同居では一致させない。
  固定DB、元案と考案入力、評価とその入力版の対応を検査し、壊れた探索は名前と理由を残した部分結果にする。
  元案・固定資料だけが欠落した記録も、他の正式保存物が残っていれば検出する。正式保存物がすべて無い探索は復元できない。
  同じ案の複製はまとめ、異なる改訂・評価、各保存場所、原文、元の目的・形式・時点、資料対応を保持する。
  一致や件数・新旧・多数決から採否を決めない。文字列による保存範囲の検索で、意味検索・現行能力や普及の再調査ではない。
  読み取り専用で、カード注記や探索の入力版へ自動追加しない。考案の参考用とし、新しい独立評価へ旧採否をそのまま渡さない。
  旧記録から事実を引用する場合は元出典と条件を確認し、必要資料を通常の添付で保存する。
  新規担当の実利用3課題で、過去判断と条件の復元・改訂と複製の区別・一致なしの範囲限定を確認した。
  これは経験を再利用する補助の採用で、新しい種の発見力の認定ではない。詳細は [検索補助の検証記録](../evals/discovery/experience-recall-01/README.md) に置く。

検査は、過去の成功例を取りこぼさないことと弱い完成案を推薦しないことの両方を扱う。
開発に使った事例は未知評価と呼ばない。能力変更前のカードは当時の本文が揃わなければ歴史再現未確認とする。
新しい入力でも公開入口から考案・追加検索・改訂・別評価まで実行し、その結果で次の実装を決める。

検査の個別の入力・正解・採点結果は [評価記録](../evals/discovery/README.md) に保存し、探索担当へ毎回渡す原則の中へ
正解として埋め込まない。ユーザーの評価と用途の範囲は引き続きカード注記と設計原則へ保存する。
比較に使う元資料と具体的な観察を保持し、型別の純増枚数から交換した個々の札や枚数を推測しない。
初回案の評価と、調査を繰り返した枝の継続判断を区別する。後者の検査では実施した調査・改訂・結果を実際に渡す。
過去のAIの結論への一致だけを目指して、価値判断を一律に厳しくしない。入力不足と判断の弱さを分けて検査する。
方式の本採用や開発完了は、文書化・機械的な検査の合格だけでは決めない。

### 3.3 探索担当の実行期限（2026-09-09）

`python -m svdeck.discovery_run SESSION OUTPUT --codex PATH --develop-seconds N --review-seconds N` は、
既存の通常考案・改訂と別評価を一度の実行でつなぐ入口（2026-09-10・試作、担当名重複で実AIの評価保存に失敗し採用保留）。
入力は保存済み探索、出力は別の保存先に追記した正式改訂1件・別評価1件とreport。
元探索の固定 → 複製上で考案・改訂 → 正式保存と入力不変の検査 → 別担当の評価 → 正式保存の回収、の順に進める。
資料を渡す既存の意味・考案指示・採否の基準を変えず、モデルや推論設定も指定しない。
担当の終了番号だけでは先へ進めず、正式入口での再検査・元資料と実装の保持を確認する。
別評価の資料は親側で履歴の原本から作り、担当側にはその固定版だけを渡す。旧評価ファイルと旧考案資料はコピーしない。
追加資料の本文に書き写された旧判断までは機械で検出できないため、意味の点検が必要という限界を残す。
失敗・未提出・時間切れは別状態で保存し、自動再試行や代理提出をしない。途中成果を残し、元の探索へは書き戻さない。
各担当は既存workerの経過時計を使い、任意の台帳接続では事前登録した工程へ開始終了を反映する。
担当名の自己申告が異なるプロセスで同じになる問題を受け、各工程の起動時に実行側の担当IDを固定する。
公開提出ではauthorだけをそのIDに結び、元の提出ファイル・申告名・本文は操作記録へ保持する。
判断・手順・根拠を代筆せず、正式保存の担当IDも起動時の設定と照合する。
元の失敗は保持し、[担当識別の修正検証](../evals/discovery/worker-identity-01/README.md)で再確認する。
実行補助の動作確認と、改訂で有用な種へ進めたかは別に判定する。
検証条件は [改訂と別評価を接続する試行](../evals/discovery/revision-runner-01/README.md) に保存する。

`python -m svdeck.worker` は、考案・調査・評価を行うローカルコマンドを実行側で監視する。
既存の探索や判定の基準は変えず、期限超過を完了・有用性・案の反証にしない。
新しい記録先に開始、期限、起動、停止要求、終了観測と標準出力・エラーを残す。既存記録を上書きしない。
期限判定は単調に進む経過時計とUTC期限の早い方。PC休止や監視側の停止中の時刻保証はできず、再開後に超過を検出する。
終了時は起動した処理と同じプロセス群の子処理へ終了要求を送り、短い猶予後に強制終了する。POSIX環境が対象。
猶予は処理終了のための時間であり、追加調査の予算ではない。途中の出力は保存し、自動で提案や評価へ昇格させない。
各工程を別の実行として起動し、後から保存を行った場合も実際の別工程として時刻を残す。
記録ファイルの存在だけで実行中・完了を判断せず、監視プロセスの終了結果と合わせて確認する。
終了直後の権限エラーは最大0.2秒の間だけ再確認する。プロセス群が存在しないという応答を得た場合だけ消滅とし、権限拒否が続く場合は終了未確認のまま残す。

任意の `--journal-root ROOT --experiment-id ID --stage-id STAGE` で、既存台帳の未着手工程へ実行を接続する（2026-09-10・実行管理用として採用）。
開始記録に成功してから担当を起動し、担当と子処理の停止処理後に工程を閉じる。起動処理開始を工程の開始とし、台帳の開始記録に要する時間も実行予算に含める。
監視ループ内では台帳へ書かない。正常終了は工程完了、それ以外は工程中断とし、停止未確認はその旨を残す。提出の成否・有用性・採否・試行全体の完了は自動判定しない。
開始は未着手工程だけ許可し、終了時は開始時に確保した工程内容との一致を確認する。他工程の更新だけなら有限回合わせ直し、同じ工程への訂正は上書きしない。
同時起動の保存順が実際の開始順と逆の場合、全体開始は観測した開始時刻の最小値へ合わせ、先行工程を期間外にしない。
ただし開始済みの試行で全体開始が未記録の場合、その不明は維持し、今回の担当開始で過去の全体開始を補完しない。
開始の記録に失敗したら担当を起動しない。終了の反映失敗は実行記録へ残し、担当が成功していた場合も監視入口は非0を返す。
停止後の再反映は担当を再実行せず、保存した実行記録から行う。台帳の再反映履歴は元の失敗記録と分ける。
画面の一覧は定期更新、詳細本文は最新版を表示する操作が必要という既存挙動を維持する。実行と記録の接続の確認を発見力の証明とは数えない。

`--clock elapsed` は、経過時計だけで作業の制限時間を判定する選択肢（2026-09-10・実行確認済み、提出までの検証は未達）。
UTC期限で止まった試行では、開始終了の時刻差28分54秒に対して経過時計は13分04秒だった。
時計差の原因は未確定。実AIは経過600秒で停止できたが、正式案0件で提出まで進む問題は解消しなかった。既定の `deadline` は従来どおり両時計の早い方で止める。
`elapsed` でも開始・終了UTCと経過秒を保存するが、固定のUTC期限は設定しない。経過時計はCPU使用時間ではなく、
OSにより休止の扱いも異なるため、実作業時間や絶対時刻の保証には使わない。担当には選んだ時計とその期限を渡し、
UTC予定時刻を実期限として誤用させない。既存の固定試行をこの設定へ変更して再採点することはしない。

## 4. オントロジー（型の骨格）

### 4.1 基本型

```
能力 = [発動要件...]  →  述語( 対象, ゾーン, 量 )
```

### 4.2 A. 発動要件（要求の母集団）

全要件を一様に記録する（ファンファーレも特別扱いしない）。各要件に
**希少度（満たしにくさ）スコア**を付け、マッチ探索の対象は希少なものだけ。
ファンファーレのような「どんなデッキでも自動で満たされる」要件は探索しない
（全カードが供給者になりマッチが無意味化するため）。

- **A1 トリガ**: ファンファーレ / ラストワード / 進化時 / 超進化時 / 攻撃時 / 交戦時 / ターン開始・終了
- **A2 リソースゲート**: 覚醒(PP≥7) / ネクロマンスN(墓場≥N) / スペルブーストN / 土の秘術 /
  コンボN / エンハンスX / 連携N / 信仰・奥義・クレスト等のクラス固有
- **A3 状態条件**: 特定カード・種族が場に / 手札枚数 / デッキ構成 / 相手盤面

A1・A2 は skill_name テーブル（公式38語）で実データ確定済み。

### 4.3 B. 述語（供給の母集団）

機械的にはフラットな型付き効果の集合。B1〜B6 の棚は人間が語彙を点検するための
見た目であり、マッチには使わない。

- **B1 除去・移動**: 破壊 / 消滅 / バウンス / 山札に戻す / 変身
- **B2 リソース**: ドロー / サーチ / カード生成 / PP増減 / コスト増減
- **B3 召喚**: トークン召喚 / リアニメイト / 直接召喚
- **B4 数値**: ダメージ / 回復 / バフ
- **B5 状態付与**: 守護 / 疾走 / 突進 / 潜伏 / 必殺 / ドレイン / オーラ / バリア / 威圧
- **B6 カウンタ操作**: 墓場+ / スペブ+ / 進化権+ / 土の印+ …

B5 はキーワードで確定済み。B1〜B4・B6 の素の動詞は地の文から抽出する
（ブレやすい領域＝人のレビュー対象）。語彙は骨格を固定し、対象の属性フィルタ等は
カードから帰納的に育てる（ハイブリッド）。

### 4.4 共通スロット

- **対象**: 所有者(味方/相手) × 種別(フォロワー/リーダー/スペル/アミュレット/自身/全体) × 属性(種族・コスト帯・名前)
- **ゾーン**: 場 / 手札 / 山札 / 墓場（EXエリアは存在しない）。**墓場は実体ゾーンでなく枚数カウンタ**、
  破壊カード参照（リアニメイト等）は別系統の**破壊履歴**を見る——抽出・デルタ分解ではこの2系統を
  混同しないこと（ルールは rules.md#墓場・#破壊履歴）
- **量**: 固定N / 変数X(源=墓場数・手札数・PP…) / 全体。**変数Xはヘッドルーム大のシグナル**

### 4.5 デルタ分解（二層の下層）

**現行実装の限界（2026-09-08監査）**: 以下の機械導出は目標仕様であり、現存の探索経路では
保存差分から副次的な用途の問いを導く処理は未実装。保存差分1347件には発動条件との接続キーがなく、
本文と照合した6枚では選択肢・時点・手札の取得枚数と純増の混在が見つかった。そのまま合計して成立判定へ
使わない。別の保存効果には条件・置換・生成の情報があるが、抽出元本文の版との一致は保証されていない。
任意で保存分析を本文の照合材料に添える案は未採用で、発見力の改善も未確認。
観測範囲と条件を変えた対照は [実装・保存値の点検](../evals/discovery/effect-consequence-audit-01/README.md) に残す。

ゾーン移動を伴う述語は**ゾーン差分ベクトルに自動分解**して保持する。
例: サーチ = `手札+1(該当) ∧ 山札−1(該当) ∧ 山札総数−1`。

これにより指定ドローの副作用でデッキ内の対象が減るような**創発供給**は、意味解釈でなく
**デルタ代数から機械導出**できる。旧「正常の侵食」はこの例だったが、2026-08-26能力変更で
無指定2枚ドローになり、デッキ純化の供給とアンカー価値を失った。
LLMの遅延抽出の役割は「変な要求文→状態述語への翻訳」だけに縮む。

### 4.6 供給/要求は語彙でなく「役割」

述語アトムはただの効果であり、**他カードの希少要件を満たす文脈でのみ「供給」と呼ぶ**。
同じバフが、普段はただの効果、「攻撃力◯以上を要求するカード」の前では供給になる。

## 5. 非対称アーキテクチャ

| 部品 | 扱い | 理由 |
|---|---|---|
| **要求アンカー** | ヘッドルーム大のカードのみ。LLMが素出力/理論最大を見積もりランク→**人が確定・追加** | 限度のあるカードに enabler を探しても想定外にならない。少数なので人手レビューが現実的＝人の主介入点 |
| **直接供給** | 全カード事前抽出→**タグ→カード群の逆引き索引** | 安い・網羅・要求から即引ける |
| **創発供給** | デルタ代数で機械導出＋足りない分だけ要求ドリブンでLLM遅延抽出 | 全カード×全副作用の事前列挙は破綻する |

**ヘッドルーム = 理論最大出力 − 素の出力**。青天井（`〜の数だけ` `〜するたび`）も、
有限でも天井が高いフィニッシャー型も両方アンカー。最大出力はたいてい条件付きで
開き、その条件がそのまま要求になる。

**アンカー選抜の目利き基準（2026-07-05・第1回アンカーレビュー由来）**:
1. **2軸で評価する: 天井の強さ × 条件の難度・特異性**。
   - 天井が弱い → 除外（例: マーロン=最大値でも弱い、エクセラ=盤面上限で+4止まり、アクシア=顔4点止まり）
   - 天井が強いが条件が簡単・標準的 → 想定内の強カード → 除外（例: 混融の団結者=超進化だけ）
   - **アンカー = 天井が強い ∧ 条件が難しい/特異/前倒しできる**（例: アマツ=3T目にクソデカスタッツが立ちうる）
2. **天井の変換先で重み付け**: リーダーダメージ/リーサル・リソース独占・コスト踏み倒し=高価値。
   **盤面除去の量的拡大=低価値**（進化権/超進化で大抵の盤面は返せる・除去カードは豊富）
3. **キーワードゲートの標準レンジは運営想定内**（奥義/解放奥義/連携10-20/スペブ等の普通の使い方）。
   想定外になるのは (a)極端な値 (b)前倒し・想定外速度での達成 (c)文脈外利用 のみ
4. **運頼みの天井は制御手段が存在しない限り不算入**
5. **既知の壁は「カード×使い方」単位で適用**。Tier1デッキの核カードでもカード自体は除外せず、
   メタと同型の使い方の種だけを後段noveltyで落とす（例: ミルティオ本体はアンカー、Tier1用法の種はNG）
6. アンカー外でも**供給側で有用なら供給登録**する（例: アクシア=低コスト自壊供給、
   スカルフェイン=ビショップ唯一のアミュ2枚以上自壊+顔ダメ→両面）
7. **バフ系（手札・山札・全体のスタッツ上昇）はアンカーでなく供給側**（2026-07-06第2世代レビュー・
   ユーザー確定）。「スタッツを上げて、それでどうするの」——バフはそれ自体で勝たず受け皿が要る。
   例: ダストデイズ(山札全体+1/+1)・侮蔑の団結者(手札ドラゴン+1/+1)は供給登録へ
8. **継続打点は「点数/ターン × 反復開始ターンからの残りターン」で天井を見積る**（2026-07-06）。
   ターン2点で中盤開始は天井不足（綺羅星却下）。1ターン目から毎ターン級の反復なら別
9. **「迷ったら残す」はnovelty判定（既出かどうかの迷い）専用**。§5の目利き基準に明確に反する候補は
   注記付きでも残さず落とす（2026-07-06・カシウス/ウィリアムを注記付きで残した反省）
10. **カード再使用・複製の相方は「強い効果」ではなく「増やす意味」で選ぶ（2026-07-30ユーザー確定）**:
   第一候補は、同名を増やすほど自身の条件・欠点を次の同名が補う**自己相乗型**（例: ゾーイは最初の
   エンハンス10で最大体力1になるが、次のゾーイも無傷化を更新するため追加の体力低下がない）。
   第二候補は、実用水準の代役がほぼなく、複製によってその機構へ構築を大きく寄せられる**唯一役割型**
   （例: ヴォーラライは実用的な「捨てられたときに働くフォロワー」として希少）。
   スペルブーストのように供給者が多数いる一般効果は、単に反復できても低評価とする。
   反復候補は同時に、(a)各回の資源を再び払えるか、(b)同一ターン内または現実的な残りターンで再使用できるか、
   (c)再使用カードの対象範囲に複製役自身が含まれるか、(d)再使用時点までに破壊履歴が汚れて対象がぶれないか、
   を検査する。どれかが破綻する理論値は候補に残さない。
   **同名クレストは重複しない**ため、同名クレストの再取得を出力増加として数えない。またモード数+を
   反復する候補は、信仰値がカード1枚につき+1しか増えないことと、残っている未選択モードがあることを
   検査する（2回目のモード数+は選択肢が3つ以上あるカードにしか上積みを作らない）。
   **2回使うだけなら通常の3枚採用から2枚引く案との差が小さい**ため、複製を核にする候補は原則として
   4回以上の反復、または反復回数に応じて同名カード自身の出力が継続的に伸びるものを優先する。
   手札を捨ててコピーする札は、コピー対象だけでなく捨て札とコピー後の手札枠まで含めて必要手札枚数を
   検査する。破壊履歴からランダム回収する札を核にする構築では、フォロワーを直接採用しないだけでなく、
   フォロワーを生成するスペル・アミュレットも回収先を汚すものとして扱う。序盤が弱い反復対象を採る場合は、
   ドロー・序盤の守り・追加の起動条件を、可能な限り破壊履歴を汚さない非フォロワーで補えるかも検査する。
11. **デッキへ複製する札は、複製後の再取得までを一組で評価する（2026-08-26ユーザー確定）**:
   山札へ同名を加えるだけでは手札も盤面も増えない。狙うカードを一意にできるかに加え、専用サーチ、
   単純なドロー、山札圧縮・自分の山札を削る効果のいずれかで、現実的な残りターン中に再取得できることを要求する。
   元コスト最大を参照する場合は、高出力カードが最大コスト帯で単独になるよう破壊履歴も管理する。
12. **能力で場に出す相方は、場に出た時点で働ける能力を選ぶ（2026-08-26ユーザー確定）**:
   プレイではないためファンファーレは使えない。ターン終了時の場出しなら、疾走・突進・攻撃時・進化時も
   通常はそのターン中に使えず価値が落ちる。常在能力、ラストワード、交戦時、場に出たときの地の文、素の大きさを優先する。
   自分のターン中に能動的に破壊して場出しを起動できる場合は、攻撃・進化に関する時間制約だけは緩和される。
13. **重複なし構築は、弱い初期デッキを完成形と決めつけない（2026-08-26ユーザー確定）**:
   条件判定時だけ重複なしにする手段、山札圧縮・自分の山札破壊で重複を消す手段、条件達成後に
   マゼルベインやサタン等で山札を別構成へ置き換える手段を探索する。素直な1枚ずつ採用との比較では、
   条件達成後の出力まで含めて採用価値を判断する。
14. **遅い復活札は、復活対象を事前に破壊する過程まで同じ勝ち筋か検査する（2026-08-26ユーザー確定）**:
   終盤まで耐えるカードの復活対象として、道中から相手リーダーへ攻める疾走札を並べても、デッキの
   進む方向が食い違う場合がある。復活後の瞬間最大値だけでなく、対象を一度破壊履歴へ載せるまでの役割、
   終盤まで耐える計画との整合、起爆ターンをほぼ準備だけに使う損失まで含めて評価する。
15. **用意された早出し手段だけで閉じるなら、着地後の伸ばし方を探す（2026-08-26ユーザー確定）**:
   同じ弾に明示的なコスト低下・早出し手段がある組は、それだけでは想定内。アンカーとして探索を続けるなら、
   早出しした本体を除去要求、追加攻撃、攻撃強化、再利用などで勝ちへ変える同弾外の相方を要求にする。
   **二枚看板＋ミロク＋ヒエンへの再評価（2026-09-06）**: ユーザーは「どう考えても運営が想定してるコンボ」と評価。
   低コスト札の生成・PP回復をプレイ枚数による軽減へ合わせる早出しは、成立ターンを訂正できても今回の発見成果に数えない。
   検索で同じ手順が見つからないことや、自分の以前の計算より早いことは、普通の使い方を超えた根拠にならない。
   本文と両側のcard_noteを照合し、既存の棄却理由を解消していない案を検算だけで再昇格させない。
   これは当該用法への評価であり、§1の「想定内の弱い構築が別の組み合わせで化けるケース」まで一律に除外する変更ではない。

16. **コントロールの防御価値を、展開量・交換可能枚数で代用しない（2026-09-06ユーザー実戦評価）**:
   セレス・アルメス構築では、盤面のフォロワー同士で交換するより除去カードで処理する方が効率的という
   評価を前提にする。小粒が攻撃で交換できるだけで「墓場肥やしとコントロールが両立」と判定しない。
   展開によって相手に除去コストを使わせる価値は相手依存であり、確定の防御として数えない。
   展開の価値は低めに評価するがゼロではなく、フォロワーを除外する条件ではない（2026-09-06追加訂正）。
   盤面に残る価値を差し引いても除去・回復・補充が優秀なフォロワーは、スペル等と同じ候補として比較する。
   墓場速度・手札の純増・防御効率・進化権消費を別々に評価する。
   これはゲームルールではなく、当該構築に対する実戦上の判定基準である。

## 6. マッチング

### 6.1 要求のコンパイル（3種）

| 種類 | 例 | 判定 |
|---|---|---|
| **イベント型** | ラストワード（味方の破壊） | 型一致: そのイベントを発生させる述語を索引から引く |
| **蓄積型** | ネクロマンス15 / スペブN | **算術**: 供給デルタ合計が期限ターンまでに閾値へ届くか |
| **存在型** | 場に土の印があるなら | 型一致: その物を置く述語がいるか |
| **構築制約型** | シャクドウ「引き直し後の手札に同コスト4枚以上」 | デッキ分布への確率的要求。供給候補=(a)分布操作カード (b)その構築制約下でも強いカード (c)制約を踏み倒すカード。カードで閉じない分は種の出力に「構築条件」として明記 |

蓄積型の変数源はゾーンの枚数のほか、**履歴カウンタ**（このバトル中に破壊された数等）や
コンボ/連携等の専用カウンタも許す（試作v0の発見）。

マッチは埋め込み類似ではなく**型の一致**（`破壊(味方)` と `破壊(相手)` は
埋め込み上は隣でもゲーム的に別物）。所有者・クラス・フォーマットの一致は必須。
**クラス固有キーワード（ネクロマンス等）はそのクラス内でのみ意味を持つ**ため、供給候補の
列挙は常に「同クラス＋ニュートラル」でフィルタする（試作v0でAIがこの違反を出したため明文化）。
ただし**ニュートラルのアンカーは全クラスを探索対象**にし、完成する候補集合ごとに
ニュートラル以外が1クラスへ揃っていることを検査する（2026-08-26、アズヴォルトで発見）。

**タグ語彙の運用（2026-07-05追加）**:
- **昇格は積極的に**: タグに無い概念を検索して有用だと判断したら、新タグとして語彙に
  昇格し該当カードへ付与する（回数基準は設けない。クエリ駆動で語彙が育つ）
- **タグは単一機構のみ**: 複合概念（例:「時間差疾走」）はタグにせず、原子タグの組合せ
  （`遅延召喚` ∧ `疾走`）で検索する
- 昇格第1号: `遅延召喚(◯◯)`（ラストワード/カウントダウン/ターン境界で後から場に出す効果。
  specific_effect側の効果は親カードに帰属してタグ付け）
- **保持/付与は別タグ（2026-07-06確定・retag.pyで機械修正済み）**: キーワード系供給タグ
  （突進・守護・疾走・潜伏・必殺・ドレイン・威圧・オーラ・バリア）は「カード自身が持つ＝`X保持`」と
  「他者に与える＝`X付与`」を必ず分ける。混同すると「付与供給」検索で自己完結カード（保持のみ）が
  大量の偽陽性になる（発見時は該当328件中約270件が誤って`X付与`だった）。抽出規約は
  docs/extraction-prompt.md §11。
- **自トークン限定付与のパラメータ分け（2026-07-06確定・retag.pyで機械修正済み）**: 「『◯◯』N枚を
  自分の場に出す。それは【X】を持つ」型（生成した自分のトークンにだけキーワードを与える）は、
  アンカーの相方（既存の別フォロワー等）には付与できない特殊形のため、汎用の`X付与`検索から
  分離して`X付与(自トークン)`タグにする。境界保留17件のうち16件がこのパターンで機械UPDATE済み
  （残り1件＝想う《力》・ソフィーナは「【守護】を持つ、進化前のフォロワー」という名詞修飾の
  未知文型で、自トークン限定パターンにも他者付与にも機械的に断定できないため判断せず境界保留のまま
  残した）。

**検索手段（2026-07-07改訂・旧3段はしごを2本に集約）**: タグは離散なので抽象クエリに引っかからない。
探索は2本立てで、**LIKE全文検索は廃止**する（skill_textのLIKEはタグ検索と同じ印刷文を読むだけで冗長・
タグ語彙の成熟で無価値化／自由文の card_note とは相性が悪く意味で読むしかないため）:
1. **タグ検索**（SQL・型一致・ミリ秒）— 語彙にある機構を確実・高速に。判定の主軸。
2. **LLM走査**（意味）— タグで拾えない未タグ概念・抽象クエリを拾う。読むコーパスは
   **`skill_text + card_note` に統一**する（従来 card_note は候補の"評価"にしか使われず"発見"に効いて
   いなかった＝§8ゴールデン事例の蓄積を検索にも還す）。card_atom由来の効果要約memoは skill_text の
   冗長コピーなので廃止（残すなら skill_text忠実+card_note に作り替え）。0件フォールバックでなく毎要求で
   回してよい（1アンカー≈1コールで全要求を一括判定できる）。
   - **タグ昇格フェーズを内蔵**: 走査で拾った未タグ概念はタグに昇格させ、以後①が機械で拾う（曖昧で高い
     LLM層が安く正確なタグ層を育てるラチェット）。**書き込みは「提案→人確認」ゲート**（誤タグでタグ層の
     信頼を汚さない・「タグはブレやすい＝人のレビュー対象」に整合。自明な完全一致のみ自動確定可）。
   - ベクトル検索/MLは検索本体に入れない（§9・想起=意味/判定=型の役割分担。826枚は全読みが近似を上回る）。

**充足マップ（2026-07-05追加）**: タグの文字列一致だけでは噛まないペアがあるため、
「要求タグ → それを満たす供給タグ集合」のマップを語彙と一緒に育てる。初期エントリ:
- `進化イベント`（「〜が進化したとき」） ← {プレイヤーの進化権使用, `自動進化付与`}
- `進化権`（【進化時】） ← 進化権の使用のみ。**`自動進化付与`では満たされない**（効果進化は【進化時】を誘発しないルール）
- `ネクロマンス(N)`・`墓場≥N` ← {`墓場+(k)`の蓄積, 破壊・スペル使用の自然増}
- `存在(◯◯)` ← {`存在(◯◯)`（カード自身）, `トークン召喚(◯◯)`}
- `死者・フォロワー` ← {死者tribeのトークン, リアニメイトで場に出たフォロワー全般}
  （動的付与のため**tribeテーブルの静的照合だけでは判定できない**。ルールは rules.md#死者）
- `リアニメイト(N)` ← 供給は**破壊履歴のみ**（このバトル中に破壊された元コストN以下の最大1枚・選択不可）。
  手札捨て・消滅は供給にならず「捨てて装填」型クロージャは全部不成立。墓地カウンタとは無関係で
  ネクロマンスと競合しない。ルールは rules.md#破壊履歴リアニメイト
- **非手札プレイで出る受け皿の価値評価はFF不発を織り込む（2026-07-07・セレス走査での適用ミス由来）**:
  リアニメイト・直接召喚・トークン召喚で場に出るカードはファンファーレ（とエンハンス）が発動しない
  （rules.md#ファンファーレの発動条件）。受け皿・蘇生対象の価値は**キーワード・スタッツ・ラストワード・
  常在能力に載っている分だけ**で数えること（例: エクセラの+X/+0はFFのためリアニでは乗らない）
- **低コスト蘇生の受け皿は複数種類を優先する（2026-07-30ユーザー方針）**: `リアニメイト(2)`のように
  構築で対象を決める効果では、主役を1種類だけに固定せず、**同じコスト上限・同じ後続の起動手段を共有する
  2種類以上**を優先して探す。片方を引けないだけで軸が止まるのを避けるためである。片方が高コストなら
  再生先の優先順位を独占すること、アイカ自身もコスト2で候補に混ざることを、候補の価値と安定性の両方で
  明示的に差し引く。さらに、主役が生成する低コスト・フォロワー（例: ルフレのフェアリー）も破壊されれば
  アイカの戻し先に混ざるため、生成物まで含めた破壊履歴の純度を検査する。複数種類が成立しない場合のみ、
  対象を引く手段を相方として探す。

**トークン能力の伝播（2026-07-07追加・現状の穴の修正）**: トークンTは別カード行（is_token=1・91体）で
T自身の supply_tags を持つが、生成カードAはTを**名前でしか**参照しない（`トークン召喚(T)`/`存在(T)`）。
抽出器はAの skill_text しか読まずTの行を見ないため、**Tの内在能力（守護・スタッツ・ラストワード・種族）が
Aの供給に伝播していない**。名前・存在ベースの要求は上の `存在(◯◯)`←`トークン召喚(◯◯)` で噛むが、
プロパティベースの要求（「守護持ちの体を場に」等）は取りこぼす（死者tribeだけ手コード済み）。
修正: `トークン召喚(T)`/`存在(T)` のTを名前→トークンcard_idで解決し、**Tの supply_tags を「(トークンT経由)」
注記付きでAの間接供給として索引に足す**（ほぼ機械・トークンは既に atom_tag 済みで材料は揃っている）。

**言い換え・下位概念変換表（2026-07-07追加・新規アーティファクト）**: 口語/抽象語 → システム語（タグ・
公式キーワード）の対応表。公式キーワード（`ability_keyword` 38語）を種に「除去 ⊃ {破壊,消滅,バウンス,変身}」
「顔詰め = リーダーダメージ」等を貯める。用途は検索のクエリ展開だけでなく**通常会話の共通語彙**にも使う。
fulfillment_map（ルール上の充足関係）とは別物＝**語の同義/包含関係**であり、別テーブルで相互参照する。
語彙はクエリ駆動で育て、確定は提案→人確認（タグ昇格と同じ規律）。

### 6.2 蓄積型の算術チェック（楽観上界フィルタ）

**現行実装の限界（2026-09-08監査）**: 以下のPP収支内で組む検査は目標仕様であり、
従来の `explore.compute_arithmetic` は自然増と各候補3枚の数量を加算するだけだった。
PPの二重使用・時間・起動条件を検査していないため、その値を楽観上界や成立PASSと扱わない。
現行出力は数量の概算に限定し、未達も確定棄却の根拠にはしない。手順の成立は別評価で検査する。
基準となる累積PPは通常のターン増加（上限10）に、期限T1〜5なら後攻の追加1回、T6以降なら2回を加える。
これはランプ・回復・軽減を含まない比較用の基準値で、カードを含む全手順の上限ではない。

```
例: アンカー「墓場の枚数だけダメージ」、T8に撃ちたい → 墓場≥15 by T8
  自然増はPP単位×デッキ形状の2プロファイル(rules.md#墓場):
    汎用 ≈ 1枚/ターン → T8で約8 / 専用構築 ≈ 0.5/PP → 累積36PPのT8で約18
  専用レートを使う場合は「その形状に寄せる」こと自体が構築制約として種に明記される
  ギャップが残るなら逆引き索引から「墓場+」候補をΔ/PP効率順に取得し
  候補×3積みの貪欲スケジュールで PP収支内に収まるか検査
```

**自然増レートは環境デッキから実測する（2026-07-06ユーザー提案）**: 上の目分量プロファイルは
暫定値。正しくは環境デッキの実リストからカウンタ寄与をコスト加重で合計して1PPあたりの増加率を
機械計算する（例: 連携=フォロワー1枚+1・トークン体数分+1、墓場=フォロワー/トークンの死亡+1・
スペル+1・墓場+(k)）。専用構築レート＝該当アーキ（連携ロイヤル・ミッドレンジナイトメア等）の実測値、
汎用レート＝全環境デッキの中央値。環境デッキDBの再取得でレートも自動追随する。

**実測レートの限界と却下の運用（2026-07-06ユーザー指摘）**: 実測レートは既存アーキテクチャの
実測値が上限であり、アンカーに特化した未知の構築はこれを超えうる。よって対話探索（explore調書）では
算術FAILを非表示フィルタにせず、**不足量（あと何枚・どのレートなら届くか）を添えて表示**し判断は人に
残す。機械的に却下してよいのは「専用構築レート＋供給候補の上乗せ込みの楽観上界でも届かない」場合のみで、
汎用レートでの不足は警告表示に留める。

**手札生成トークンのPP会計（2026-07-06ユーザー確認済み）**: `手札生成(X)` のXがフォロワー系
トークンの場合、寄与を連携+1・墓場+1計上し、**分母（PP）にそのトークンのプレイコストを加算する**
（手札に加わったトークンは後でプレイされて場に出て死ぬ・そのPPも払う、という会計。
例: ヴァンプキーボード・ルルミ=(本体1+バット1)/(2コス+バット1PP)≈0.67/PP）。
`トークン召喚(X)` は場直行なので分母加算なし。体数は card_atom.atoms_json の
effect欄 `トークン召喚(X, N)` / `手札生成(X, N)` から抽出し、同じタグが複数effect
（FF+進化等）に出る場合は最大値（条件付き重複発動を常時扱いにしない）、抽出不能は1体近似。
実装は bench.py の実測レート計算（v5）。

- **楽観上界**（必要札は引ける・最高効率で回る前提）で「それでも届かない」組だけ却下。
- 通過＝実用の保証ではない（④の仕事）。落ちた＝確実に死んでいる。
  リコールを守りゴミだけ減らす方向にしか間違えない。
- **消費の会計（2026-07-05確定ルール反映）**: ネクロマンスは墓場を消費する。クロージャ内に
  消費側が複数いる場合、要求は個別でなく**消費合計 ≤ 供給合計**で見る。
- **PP収支の上界**: 後攻はエクストラPP（T1〜5で+1を1回・T6以降で+1を1回・任意タイミング）を
  楽観側に含めてよい。ルール前提の正準は docs/rules.md（旧: extraction-v0.md §0から移管）。
- **盤面継続の会計（楽観上界への例外＝悲観固定）**: **残存性のないフォロワーが次の自分ターンまで
  生存する前提のクロージャは、楽観上界でも不成立として落とす**（根拠は rules.md#盤面継続の原則）。
  生存を仮定してよいのは残存性がある場合のみ（潜伏・威圧・オーラ等。アミュレットは適用外）。
  同一ターン内で完結するコンボはこの制約を受けない。

### 6.3 提案単位 = 要求クロージャ（ペアではない）

アンカーの希少要件は複数あり、1供給では閉じない。提案単位は
**アンカー + 全希少要件を閉じる最小カード集合（同クラス・PP収支成立・3〜4枚以内）**。
要件ごとに逆引き索引から候補群を出し、全要件を同時に閉じるセットを組む。
1枚で2要件を満たすカードは優先。同じ索引で「パーツを拾えるサーチが同クラスに
いるか」（一貫性）も機械チェックできる。

### 6.4 逆方向マッチング（供給起点・2026-07-07追加）

通常は「アンカー→供給」で引くが、逆に**供給起点**の経路も持つ: 狭い/変なカード1枚を指定し、
「このカードは anchor_require のどのactive行（希少要求）に噛むか」を逆引きする。ほぼ機械（型ベース・
48行で即動く）。design §7「狭く変な供給が変な要求にピンポイントで噛むほど高評価」を正面から狙う経路。

### 6.5 環境デッキ補強（②）の探索方針（2026-07-16ユーザー確定）

**自明なかみ合いは調べる価値がない**: 「秘術→土の印」「ネクロマンス→墓場」級の周知のかみ合いは、
環境デッキなら既に採用済みか意図的に不採用が結論済み。条件↔資源の機械対応表で網を張る案は
この理由で却下（2026-07-16）。調べる価値があるのは**非自明な要求・欠損**だけ。探索は2方向:

1. **デッキ要求の発掘（アンカーの弱い版）**: 環境デッキに対して「アンカーほど尖ってないが、
   このデッキはこういう供給が欲しいのでは」という要求をLLM＋人で起こし、既存の供給探索
   （explore/fulfillment_map）で引く。アンカー基準（§5）のデッキ版
2. **デッキプロファイル（スキーマのデッキ集計）**: card_vschema を40枚分デッキ単位に集計し、
   回復・盤面処理・リーダーダメージ・横の体数などの量を見える化する。偏り・欠損が1.の
   要求候補を機械的に示唆する。集計器は vector.py（§11.10で凍結したB3）の解凍＝使う側の出現

**方向2は②の探索手段としては撤退（2026-07-16ユーザー判定・実物レビュー後）**: ランプドラゴンで
実出力を検収した結果、値の大半が条件付き（最低22→最高79のような幅）で条件に依り過ぎ、
数値としてデッキ間比較・欠損検出に耐えない。新しい組み合わせがここから見つかる見込みも薄い。
**profile.py はデッキ分析ツール（未知デッキの回復・打点・ドロー構造を人が読む用途）として残す**が、
②の探索は方向1（デッキ要求の発掘→供給探索）に一本化する。

#### 6.5.2 方向1の具体化: デッキは供給の束かつ要求の束（2026-07-16ユーザーと確定）

デッキのパーツは要求にも供給にもなる。よって探索はデッキを2つの束に畳み、単体カードの逆側と
タグ型一致で突き合わせる（材料は既存資産: atom_tag の supply 813枚/require 430枚・fulfillment_map・
explore/reverse の型一致判定器）:

- **方向A（本命・先行実装）**: デッキ=供給の束 × 外のカード=小さなアンカー。デッキの副産物
  （墓場・トークン横並べ・進化回数・PPブースト…）の供給タグ束に、**要求タグを持つ外のカード**の
  要求が型一致するかを引く。reverse.py のデッキ版。「狭い条件のカードが、このデッキでは条件が
  タダ同然」を探す
- **方向B**: デッキ=要求の束。デッキ内で充足がギリギリの要求を洗い出し、太らせる外の供給を
  explore 流用で引く
- **自明対策=希少度ランキング**: 要求タグごとに「それを満たせる環境デッキ数」を数え、
  少ないほど上位に出す（進化権のような万人向け要求は自動で沈む）。自明さの絶対判定はしない。
  最後は novelty 壁（§7）と人の目利き

**1周目の結果（2026-07-16・テンポエルフ/進化ビショップ/スペルウィッチ）**: ヒット15件・採用0。

#### 6.5.1 デッキプロファイル第1弾の算出方針（2026-07-16ユーザー確定）

スタッツ・盤面処理は計算が難しいので後回し。まず**リーダーダメージ・回復・リソース力**の
3軸の算出方法を確立する。共通前提: **随伴・トークンの効果を漏らさない**（生成されるトークン自身の
キーワード・効果まで解決する。例: バット=1/1ドレイン。FF不発の規律は維持）。

- **リーダーダメージ**: 疾走打点＋バーン（相手リーダー対象ダメージ）の合計。**進化権は機械では
  考えない**（疾走進化の+2/3は、デッキ内の進化権競合と盤面用途に依存するため。人が場合に応じて
  後から足す前提の基礎値を出す）
- **回復**: 無条件の数値回復のみ機械で合計。**条件付き回復（ドレイン等）は機械算出を諦め、
  素材（カード名＋起動条件）をデッキ単位で列挙して人/LLMが個別に見積もる**。判定知識:
  ドレイン=攻撃時の条件付き回復／場残りして次ターン攻撃する分は回復に数えない／
  突進・疾走の付与（徒姫等）や進化（攻撃力分回復・進化権消費）、リアニメイト+進化（フェディエル）が起動手段
- **リソース力**: カード1枚のリソース力 r = コスト + 手札に加えるトークンのコスト合計 +
  ドロー枚数n×A + 個別変数（特殊な手札加算）。A=デッキ平均リソース力は自己参照だが
  不動点として代数的に解ける: A = (コスト総和+トークンコスト総和+個別変数総和) / (40 − ドロー総数)。
  **デッキ指標は平均A（=手札1枚の消費あたり使えるコスト量）を使う**。総和はドローで引いた
  カードのコストを二重計上するので使わない。**融合用など素で使う想定のないトークン
  （財宝・バーストコア等）は人手の除外リストで弾き、残りは額面コストで数える**

**壁の基準は「一般に広まっているか」であって「誰かが試したか」ではない（2026-07-05確定）**。
よって既出判定は攻略サイトのWeb検索＋ユーザー知識で足りる。**Deck Portal共起オラクルは
novelty壁としては過剰に厳しい**（広まらなかった良デッキを弾いてしまう）ため壁には使わない。
残る用途は逆向きの発見支援（共起が高いのに攻略サイト未掲載のペア＝誰かが見つけた未拡散の芽）
のみで、優先度低のオプション扱い。

**運用ルール（2026-07-05・種ループ1〜2周目の教訓で更新）**:
- **主判定＝ローカルの環境デッキDB**: gamewith/game8のTier表から環境デッキ（名前/Tier/更新日/
  40枚リスト）を収集して meta_deck テーブルに持つ。ペアの既出判定は「この2枚が同居する
  環境デッキがあるか」のSQLで即答（全ペアに対してコストゼロ）。定期再取得で鮮度を保つ
- **Tier表DBの限界（2026-07-05・3周目で実証）**: Tier表由来の45デッキは、Tier表外で確立済みの
  アーキ（薔薇エルフ・ライオウィッチ・OTKウィッチ・マゼルベイン等）を検出できない。3周目の
  スポット確認9本中5本が「DB共起0なのにWeb既出」だった。**共起0は「未踏」を意味しない**。
  DBの役割は「環境結晶化の強警告」判定に限定し、提示予定の種は全件Web確認を必須とする。
  根治は meta.py の取得範囲を各サイトの「デッキ一覧ページ」（Tier表外レシピ含む）へ拡張すること
- **Web検索はスポット確認に降格**（環境デッキ表に無いが既出の匂いがする場合のみ、1周2〜5回。
  ただし上記の限界により、種として提示する組み合わせに限っては全件Web確認する）
- **フィルタしない**: 調査結果（ヒットなし/ネタデッキ枠/環境デッキ）は種に添えて全部ユーザーに見せ、
  棄却判断はユーザーが行う。強い警告は「現環境デッキとして結晶化している」場合のみ
- ヒットなし・ネタデッキ枠ヒットはどちらも想定外候補として健全なシグナル
- 種の提示**前**に既出調査を済ませる
- **既出壁に当たったペアの再浮上条件（2026-07-06・4周目ユーザー確定）**: 壁に当たった組は
  (a) 既存の環境デッキ・先駆者が使っていない**別の要求達成手段**が見つかった場合、または
  (b) 新弾でそのデッキの**パワーを底上げする新カード**が出た場合のみ再考する。
  同じ達成手段のまま「単に使う」だけの再提案はしない（例: ベリアル=既存進化NMに無い
  進化カウントの稼ぎ方が要る／SLG×シンセライズ=先駆者ありのため底上げ新カード待ち）

- **共起オラクル**: Deck Portal全投稿デッキからカード共起回数を集計。
  「②で噛む ∧ 共起が少ない」= 想定外候補。
- **閾値は緩め**: デッキ情報は二極化する（強いデッキはシェアされ、そうでないものは
  広まらない）ため共起0は厳しすぎる。数件の共起は許容し、本命の壁は
  「大会/Tierデッキに結晶化していないこと」に置く。
- **ハブ供給の減点**: 万能サーチ/ループ等の「何にでも刺さる」供給とのペアは
  想定外にならない。狭く変な供給が変な要求にピンポイントで噛むほど高評価。

## 8. 人間との共著ワークフロー

全自動を目指さない。役割分担:

1. LLMが抽出を**過剰気味に**下書き（漏らすより出しすぎに倒す）
2. 人は全826枚を見ない。**②③を通って候補に絡んだカードだけ**抽出を遅延レビュー
   （創発供給の補正=指定ドローから対象カード減少を導く型の修正が人の価値）
3. アンカー選定は人が最終確定（少数なので現実的）
4. **ゴールデン事例の蓄積**: 人の抽出修正・④での判定コメントをDBのユーザレイヤ
   （card_note / card_tag。再クロールで消えない）に保存。抽出プロンプトの回帰テスト
   と④のfew-shot教材にする。教育をチャット履歴でなくデータセットにする。
5. **フィードバックの2層記録（2026-07-05ユーザー永続指示）**: 会話でユーザーの訂正・評価・
   ルール知識が出たらその場で振り分けて永続化する——**ゲームルール→rules.md／設計判断→
   このdesign.md／カード固有→card_note**（追記式・上書き禁止）。運用の詳細は `.claude/CLAUDE.md`。
6. **蓄積の最大活用（2026-07-05ユーザー指示）**: 記録するだけでなく毎回読ませる。
   **全LLM工程（抽出・アンカー選抜・要求コンパイル・目利き）のプロンプトには rules.md 全文と
   対象カードの card_note を必ず含める**。サブエージェントへの委譲プロンプトも同様。
7. **自己改善ループ（2026-07-05確定・構築中）**: ①回帰ベンチ＝環境デッキを教師データに
   要求充足の見逃しを機械採点（リコール率で改善を測る）→ ②語彙・充足マップの昇格 → ③要求の
   永続化とイベント駆動再コンパイル。人の目利き・ルール確定が教師信号で、完全自動は目指さない。
   ③の運用: **新弾取得後は `python -m svdeck.require recheck` を回す**（2026-07-06追加）。
   anchor_requireのdead/active各行をタグ語彙・fulfillment_map経由で再検索し、「前回dead判定だが
   今は供給が存在する」変化点だけをレポートする（DBは変更しない・判断は人とメインセッションの仕事）。
   公式の能力変更後は **`python -m svdeck.fetch --refresh`** を回す（2026-08-26追加）。一覧の全カードを
   手元と突き合わせ、変わった既存カードだけ単体APIの完全な値で更新する。利用者のメモ・タグは保持し、
   効果が変わったカードは古い分析を勝手に消さず、再作成が必要なcard_idとして報告する。
8. **アイデアの恒久保存（2026-07-07ユーザー指示）**: 台帳の本体 `data/cards.db` は権利物同梱回避で
   git管理外（`/data/`は.gitignore）。**未成立アイデアは新弾で解ける可能性があるため全て残す**——
   dead行も「失敗理由＋どんなカードが来れば再浮上するか」をnoteに保持する。恒久ミラーとして
   `src/svdeck/data/anchor_require_ledger.json`（全48行の完全スナップショット・git追跡）を置き、
   台帳を更新したら書き出し直す。復元は `python -m svdeck.require load` で再取り込み。

## 11. 戦闘力ベクトル（カード強度の数値化・2026-07-10ユーザー提案でロック）

**目的**: §5アンカー選定と④目利きの「強い/弱い」を目分量から再現可能な数値へ。副次的に §5の
ヘッドルームを数値化し、②meta shell 2軍（下記11-4）の限界価値評価を可能にする。

### 11.1 コストを単位にしない（設計の起点）

カードの強さをコスト換算（「コスト3.7相当」）**しない**。理由2つ:

- **非線形**: コスト9はコスト3の3倍の強さではない。初めて出せるのが9ターン目で、その1ターンを
  丸ごと使う＝ハイコストは超線形に強くあるべき。出力をコストで割ると、この歪みを数字が背負う。
- **インフレ**: コストが表す強さは環境で動く。コストを固定基準にすると時代の流れに追随できない。

帰結: **戦闘力は絶対量（ゲーム効果そのもの）で測り、コストで正規化しない**。割り算をやめた瞬間に
非線形の歪みが消え、ハイコストは絶対インパクトの大きさとして自然に高く出る。コストは別軸として
必要な時だけ対にする（効率＝インパクト/コスト）。

### 11.2 三層構造

1. **ベクトル（一次データ・保存）**: 軸ごとの最低値/最高値の幅。コストフリー・客観。カードの素性。
   §4.5デルタ分解の型付き量を軸へ集計して作る。最低値=無条件で出る分 / 最高値=enabler込みで
   伸ばした最大（=§5ヘッドルームの中身＝伸びしろ。最高値−最低値を数値化したもの）。
2. **スカラー（射影・その場計算）**: `ベクトル · 重み`。カード同士の比較・順位付けに使う。
3. **文脈重み**: 軸の価値は**逓減する**（回復/リソースが過剰なら5枚目は1枚目より安い）。よって
   スカラーは1カード1値でなく文脈依存。2モード:
   - **真空（デッキ無し）**: プラン別の固定重み（アグロ/コントロール/コンボの数レンズ）で射影。
     カードを数レンズで並べる。飽和させるデッキが無いので逓減はまだ効かない。
   - **デッキ文脈**: 重み＝そのデッキの**不足分**（既に過剰な軸は重み≈0）。これが限界価値。

ベクトルは客観・重み付けは判定、という本設計の思想（型=客観／目利き=主観）と一致。**スカラーへ
早期に潰さず、比較が要る時だけ明示的な重みで潰す**（軸間の換算率は差し替え可能に保つ）。

**伸びしろは発動条件付きで持つ（2026-07-11ユーザー確定）**: 最高値は「何を満たせば届くか」の条件
（atomのrequires）を各増分に添えて保持する。数字だけでは無意味＝「顔20（要: クレスト＋ラストワード）」の
ように天井と条件はセット。条件の難度＝§4.2の希少度。これが §5アンカー基準『天井の強さ × 条件の難度』に
直結し、**天井を開く条件そのものが②の探す希少要件**（§11.5・anchor_require台帳）になる。

### 11.3 ベクトルの軸（叩き台・クエリ駆動で育てる）

戦闘力ベクトルの成分＝評価軸。**すべてフラットに並べ、終端/中間・直接/間接・フィニッシャー否かの
ような階層を構造に持たせない**（2026-07-11ユーザー確定）。「どの軸が効くか」はデッキ次第であり、
それは11.2のスカラー化の文脈重みで表す。構造で先取りしない。

初期の軸: リーダーダメージ / **攻撃力 / 体力**（自フォロワーの盤面圧・場持ち）/ 回復・軽減 /
カード枚数（アドバンテージ）/ **コスト(PP)** / **進化権 / 超進化権** / **除去**（下記の構造で保持）。
各軸は固有単位のまま持ち、共通単位へ正規化しない（軸間の換算はスカラー化時の重みでのみ行う）。
**テンポ軸は曖昧なので廃止**（2026-07-11ユーザー）。

- **攻撃力と体力は合算しない**（2026-07-11ユーザー確定）。攻撃＝打点・戦闘で取る力／体力＝場持ち・
  除去耐性で役割が違う。配分の偏り（例 10/1 と 3/4）でも価値が変わる（非加法）。この非加法性は
  1数字に潰さず、攻撃・体力を別軸で持って重み・判定側で扱う。
- **スタッツ・除去は縦／横を分ける（2026-07-11ユーザー）**: 縦＝単体の大きさ／横＝体数・広がり。
  スタッツ＝(体の大きさ, 体数)、除去＝(殺傷力, 到達[単体/全体])で対応。**横スタッツは全体除去に、
  縦スタッツは単体確定除去に対応される**（除去とスタッツは鏡）。※現vectorizerはスタッツ合計のみ＝
  体数・縦(最大単体)の分離は要追加。
- **PP＝符号なしの実コスト**（2026-07-11ユーザー確定）。ベクトルでは 2, 8 のような素の数字（自己コスト減を
  引いた後の実コスト）。−で足し込まない。ramp（他カードのPP産出）の扱いは運用時に詰める。
- **進化権・超進化権は符号付き＝消費−／産出＋**（2026-07-11ユーザー確定）。数えた価値が進化時に乗る
  （実質的に進化権を要求する）カードは進化権−1、超進化時なら超進化権−1。回復・付与するカードは＋1・＋2。
  **両者は別軸**。同一体で進化と超進化は同時にできないので両方−1しない。
- **除去は「殺傷力 × 到達」を効果ごとに保持**（2026-07-11ユーザー確定・掛け算で1数字にしない）:
  - **殺傷力**: ダメージN（体力N以下を処理）または **確定**（破壊・消滅・変身＝サイズ無制限で1体）。
    確定は「到達∞ダメージ」を無限記号なしで表せないため別枠（サイズ無制限性が独立軸の理由）。
  - **到達**: 単体=1 / 反復K回=K / 割り振り=配れる数 / **全体＝フラグ**（盤面体数を掛けない）。
    総火力（ダメージ×体数）は却下——体数仮定がガバく、単体大打点と範囲が同じ数字に混ざるため。
  - 例: 単体10点=(10,1) / 全体2点=(2,全体) / 3点2回=(3,2) / 割り振り6点=(≤6,≤6)。1枚に複数あればリスト。
  - バウンス・変身はサイズ無制限だが恒久で消せないため確定より軽い（正確な軽さはフェーズ2）。
- **リーダーダメージと回復・軽減は同一軸の符号違い**（自他の残機スイング）。ベクトルでは別スロットで
  持ち「同一軸」と注記する。
- **疾走は攻撃力をリーダーダメージに数える**（2026-07-11ユーザー確定）。出たターンに顔を殴れるため。
  突進は顔に行けないので盤面側のまま。これがキーワード処理の方式(a)＝軸の付け替えの具体例。
- **エンハンス・結晶・進化はモードで持つ＝1カードに複数ベクトル**（2026-07-11ユーザー確定）。コストや
  条件で別物になる版は、最低→最高の1本の幅でなく「(実コスト, ベクトル)」を並べて持つ（PPと効果が常に
  セットで動く）。コストを変えないenabler（コンボ・覚醒・スペブ等）は各モード内の最低→最高の幅で表す。
- **最高値に無限記号は使わない**（2026-07-11ユーザー確定）。真の青天井は実在しない前提。「〜の数だけ」
  系も、必要なら実測レート由来の**実用上限**を入れる。
- **トークン等の召喚体を軸に足すときは「そのまま場に出て効く分だけ」**（2026-07-11ユーザー確定）。
  スタッツ・キーワード・ラストワード・常在能力は数え、**ファンファーレ／エンハンスは数えない**
  （非手札プレイでは不発。§6.1「非手札プレイで出る受け皿はFF不発を織り込む」と同じ規律）。
- **リーダーダメージの重要度もデッキ依存**: ビートダウンは高く、ワンパン/OTKコンセプトは逐次の
  小打点を要さず低い（フィニッシャーが一括で出す）。「フィニッシャーか否か」は独立カテゴリでなく、
  この軸の大きさで表れる二値でない量。

**運用注意（2026-07-11ユーザー指示）**: この軸構成（特に除去の殺傷力×到達、モード分解）は叩き台で、
全カードへ当てて実際に使う段階で不整合が出うる。**運用で問題が出たら軸・単位を見直す前提**でメモとして残す。

### 11.4 軸間の重み付け（フェーズ2・未確定）

**却下（2026-07-11ユーザー）: バニラ曲線／適正コスト単機能カードを基準にする案**。コストに再アンカー
するため、脱コスト（11.1）の目的と循環する。

フラットな軸を1スカラーへ潰すときの軸間換算（重み）は最難所として**フェーズ2に隔離**し、現時点で
確定しない。候補の錨（未採用・park）:

- **固定の勝利ライン（リーダーHP20）**: インフレしても器の容量20は不変＝インフレ耐性の候補。ただし
  **リーダーダメージは終端でなく回復と打ち消し合う競り合い**であり、単独では勝利条件にならない
  （「終端通貨」概念は却下・2026-07-11）。盤面・カード・テンポを固定ラインへ換算する率は未解決で、
  これがフェーズ2の本体。

**価値モデル（2026-07-11ユーザー・フェーズ2の背骨）**: 全価値は2レースに流れ込む（固定ライン20＝ライフ
スイングの具体化）。

- **キルレース(攻め)**: 相手ライフを0に。素材＝リーダーダメージ(リーチ)＋スタッツ(相手が無視した分)。
- **生存レース(守り)**: 自ライフを守る。素材＝回復・除去＋スタッツ(相手が処理に回った分)。

軸の性質:
- **リーチ(リーダーダメージ)＝飽和でなくキルレースのゴール寄与**。閾値＝相手の実効ライフ(20＋相手回復)。
  超えたら勝ち＝「どう満たすか」の話であり飽和とは別。
- **除去・回復＝生存レースの飽和素材**（相手盤面／相手打点まで。超過は無駄）。
- **スタッツ＝両レースに効く変換器**。相手の除去力を超えた分だけ有効。
- **リソース・PP＝各ターンの充足**（総量でなくカーブ・重いカードは後半のみ。全ターンで足りるか見る）。

**除去・スタッツ・回復・打点の価値関係（2026-07-11ユーザー指定メモ）**:
- 基本の1点効率: **除去 ＞ スタッツ**（除去の方が軽い）。
- スタッツは相手の除去力を**超えた分だけ**が回復・打点に変換される。その超過分は **スタッツ ＞ 回復・打点**
  （押し付けた盤面圧は素の回復/直接打点より効率的）。
- **超えなくても最下位だが正**: スタッツ≤相手除去でも相手に除去を強要する（相手もコストを払う）。ただし
  除去＞スタッツの不利トレードなので価値は一番低い（損切りではない）。
- **目標**: 超えても除去された分は不利トレード(相手除去＞自スタッツ)を食らうので、超過分を回復・打点に
  化けさせてそれを取り返すのが目標。
- 価値順: **除去 ＞ スタッツ(超過) ＞ 回復・打点 ＞ スタッツ(非超過)**（すべて正・非超過が最下位）。
- **この価値順は"重み"でない（2026-07-11ユーザー訂正）**: 除去/スタッツ/回復/打点を1スカラーへ足す係数
  ではなく、"スタッツが文脈でどう化けるか"の下流の考え方。**4つは別軸のまま持ち、重み付き和で潰さない**。
  強さは単一点数でなく**素材プロファイル**（早すぎる collapse をしない＝§11.2と同じ規律）。

**静的メトリクスの境界（重要）**: スタッツが回復に化けるか打点に化けるかは相手の除去力・対応次第＝相互作用＝
シミュレーション領域（§1非対象）。よって**静的なカード点数では変換まで解かず、各カードが2レースへ供給する
潜在素材まで**を測る。変換（どっちに化けるか）はデッキ＋対面依存＝人／文脈の層に置く。

**フェーズ1（ベクトル化）はこの重みに依存しない**。軸ごとの量（最低値/最高値の幅）を抽出するだけで進める。

### 11.5 ①→②の接続

「デッキの不足分で重み付けした限界価値」（11.2の文脈重み・デッキ文脈）は**meta shellアンカー
（②2軍）そのもの**。既存の強いデッキに載せた限界貢献を測る＝文脈=meta shell を入れるだけ。
よって①（数値化）が②の前提。順番は①→②。

### 11.6 スコープ境界と未解決

- **判定層のみ**: この数値化は §5アンカー選定と④目利きの補助。**§6マッチングには入れない**
  （型一致・スコアリングしない・ML入れない＝§9-F の背骨を侵さない）。
- **交換レートが主観の核**: 通貨間（顔ダメ1点 vs 手札1枚）の換算はプラン依存。だからベクトルで持つ。
- **非数値の強さ**: 守護・潜伏・妨害・勝ち筋の唯一性など、素の数値軸に落ちない価値の扱いは §11.7。

### 11.7 キーワード・機構の軸への載せ方（2026-07-11ユーザー確定・網羅監査由来）

全効果の**38%は素の数値軸に乗らない**（監査: 未カバー158種）。性質別の扱い:

- **前提の訂正（重み送りの明確化）**: フェーズ2のスカラーはベクトルから組む。よって**価値を持つものは
  必ずベクトルに入れる**（フラグでも）。「守護等を軸に入れず重みだけで」は誤り＝ベクトルに無いものは
  重み付けられない。キーワードはフラグとしてベクトルに載せ、価値の重みだけフェーズ2で決める。
- **攻撃は単一予算・キーワードは使い道を開くフラグ（二重計上しない）**: 1体の攻撃力は「顔／盤面トレード／
  場に残す」のどれか1つにしか使えない。攻撃をリーダーダメージと除去へ同時加算しない。キーワードは予算の
  使い道を開くフラグ＋代償で持つ:
  - **疾走**: 攻撃を顔に出せる（顔は殴り返さない＝ノーリスク）。
  - **突進**: 攻撃を盤面トレードに出せる。**交戦＝殴り返しで自分の体力が減る／死ぬ**。
  - **必殺**: 交戦・サイズ無視＝交戦の確定除去。
  - → 除去エントリに **一方的／交戦** フラグ（スペル除去=一方的、突進・必殺=交戦・体を差し出す）。
  - **ドレイン**: 回復だが攻撃を通せて初めて。疾走/突進が無ければ即使えず、そのターン使うなら進化権を
    食う（進化で盤面を殴れる）→ **即効／遅延（遅延=進化権要求）** フラグ。
- **生存キーワード（守護・潜伏・オーラ・バリア・威圧）**: 数値でなくフラグでベクトルに持つ。体力が守りに
  効く度合いを表し、価値の重みはフェーズ2。
- **カウンタ資源（スペブ・土の印・信仰・カウント・PP最大+ 等）**: 符号付きの産出量として軸にする
  （進化権と同類・ベクトル化しやすい）。
- **妨害（守護剥奪・行動制限=フリーズ・手札破棄・デバフ・相手への付与）**: シャドバでは数が少ない→
  専用軸でなく**その他（妨害）枠**（フラグ＋短い記述）に集約。増えたら軸へ昇格。
- **付与（他の体にキーワードを渡す）＝対象で3分岐**（区別はデータに既存＝§6.1のX付与／X付与(自トークン)）:
  - **自トークン・自身へ** → 自己完結。その体の軸にキーワードフラグ込みで畳む。
  - **他の味方へ** → **供給フラグ**（値は相方次第で固定数字にしない・組み合わせで実現）。これがカードを
    enabler（種の相方）にする印＝§4.6・アンカー/供給システムと直結。
  - **相手へ** → 妨害＝その他枠。
- **召喚・蘇生**: 召喚（トークン/直接召喚）は出る体のスタッツを軸に足す（FF不発を織り込む・§6.1）。
  進化/自動進化/超進化は進化権・超進化権の消費＋スタッツ／能力の変化として計上。
- **リアニメイト＝文脈依存フラグ**（2026-07-11ユーザー確定）: 出る体はデッキ次第（蘇生対象は構築で決まる）
  ＝それ次第すぎるので**固定スタッツを置かずフラグのみ**。値はデッキ文脈で決まる（付与supplyと同じ扱い）。
- **カウントダウン系（クレスト含む）＝モードでなく時間差**（2026-07-11ユーザー確定）: 「出す→数ターン後に
  発動」は別モードにしない（プレイの選択肢が変わるわけでなく遅れるだけ）。**発動効果は軸に数えつつ
  「遅延Nターン」フラグを付ける**。クレスト付与・カウントダウン(N)自体は値でなく発動のお膳立て（setup）。
  これで「他モード産物に依存する効果が素モードに漏れる」問題（例ベリアル顔20）は、漏れでなく遅延つき
  条件つきの天井として正しく表れる。
- **構造（モード・選択・対象選択）**: 値でない＝軸に載せない。モードは11.3のモード分解、ターゲットは
  効果の付帯情報で持つ。
- **要確認**: クレスト付与(60件)は「キーワード付与」でなく Bishop のカウンタ資源の可能性。マッパー作成時に
  実データで振り分ける（カウンタ資源ならベクトル化側）。

### 11.9 フィニッシャー（勝ち筋）の数値化（2026-07-12ユーザーと確定・未実装）

**動機**: 既存軸は「素の打点の大きさ」しか測らず、**勝ちを畳む力**を取りこぼす。毎ターン顔2点（遅い）と
9ターン目に一撃20点（バースト）が同じリーダーダメージ軸に足されて区別が消える。フィニッシャーの価値は
**「何ターン目に試合を終わらせられるか」**という時間軸にある。これを数値化する。

**新軸は作らない＝リーダーダメージ軸の最高値（幅の上側）で表す**（2026-07-12ユーザー確定）:
- フィニッシャー＝「リーダーダメージ軸の高い最高値」。1ターンに顔へ通せる実質打点のピークを最高値に載せる。
- **特殊勝利＝リーダーダメージ 20**（勝ちラインちょうど＝満タンから確実に勝つと同義）。100等の外れ値はやめる
  （下流計算のノイズになる・2026-07-12ユーザー訂正で100→20）。回復を無視する真の特殊勝利だけ、必要なら
  「回復無視」フラグ1個で後から区別（当面はフラグ無し・20のみ）。
- **20ちょうどを要求しない**（§11.4キルレースの再確認）: シャクドウ等の16点級は生の数字16のまま持つ。
  20は物差しで要求でない。20以上＝満タンから一撃／20未満＝前もって削れば勝ち（残ライフ≤バースト値で勝ち）。
  16は欠陥でなく「他で4点削れ」という素材プロファイル。二値化・20丸めは情報を消すので禁止。

**バーストの2源**（お膳立て型の測り方・2026-07-12）:
- **本体分（自己完結）**: カード自身が1ターンに顔へ出す分。直接顔ダメ＋疾走攻撃は**既存リーダーダメージ軸に既出**
  （読み替えるだけ）。複数回攻撃はその疾走分を倍化。盤面（疾走なし）は**次ターンの顔打点**として実質打点へ読替。
- **お膳立て分（供給・ローズクイーン型）**: 打点が他カードから湧く。変身/召喚/踏み倒しで**生成物を名前解決で追い**
  （既存機能）、生成物の顔出力×枚数。ローズ→薔薇の閃撃(顔3)×N。**枚数Nは静的に決まらない**（手札・構築次第）
  ＝§11.4の相互作用境界。型（3点×N の構造と単価）は自動抽出、**Nは専用デッキ想定の見積り**で最低〜最高の幅に。
  ローズなら リーダーダメージ 15→21（最高値＝コスト2以下エルフ7枚の想定）。これは§11.7の供給フラグと同族。

**即決／猶予フラグ**（2026-07-12）: バーストのタイミング印。**即決**＝このターン（疾走・バーン呪文）／**猶予**＝
次ターン（盤面が生き残れば・相手に1手渡す）。猶予は撃てるターンが＋1され信頼度も落ちる。盤面フィニッシャーは猶予。

**複数ベクトル vs 幅の判定ルール**（§11.3の再確認・2026-07-12ユーザー確定）:
- **コスト/発動タイミングが変わる → 複数ベクトル（モード）**。既存: 素/進化/超進化/エンハンス。
- **同じプレイで量が動くだけ → 最低〜最高の幅**。ローズの15→21、覚醒/奥義/スペブ等の条件は全部これ。
- ∴ ローズは幅で持つ（15/18/21の3ベクトルにしない＝モードの誤用・中間点が恣意的・カード増殖）。

**発動ターン軸（新規・2026-07-12ユーザー提案でロック）**: PP（プレイのコスト）とは別に、**条件が揃って最高値が
撃てるようになるターン**を最低〜最高の幅で持つ独立軸。
- **PPと別物**: PP＝そのプレイ1回のコスト（カーブ・効率用）／発動ターン＝最高値が開くタイミング。3コスの覚醒
  カードはPP3だが最高値は覚醒する5ターン目以降。ローズはPP9だが21点は7枚揃う10〜11ターン目。PP同じでも発動ターン
  は違う。
- **条件の難しさをゲーム本来の単位（ターン）で測る**＝§4.2希少度／§5アンカー『天井の強さ×条件の難度』の難度側・
  フィニッシャーの「何ターンで勝てるか」に同一軸で直結。フィニッシャー専用でなく**全条件付き最高値に効く汎用軸**。
- **幅**: 最速側＝専用デッキ＋好ドロー＋ランプ（PP踏み倒し）込み／現実側＝その専用デッキの平均。
- **粒度**: 当面は最低値ターン（≒出せるターン≒PP）と最高値ターン（＝発動ターン）の2点。増分ごとには割らない。
- **算出**: 一部は自動（PP→ターン・覚醒→5・エンハンスN→N）、一部は専用デッキ想定の見積り（スペブ枚数・お膳立て
  枚数）。バースト値の枚数Nと同じ「自動＋人の見積り」の混合。
- 出力像: `リーダーダメージ 最高値21 @ 発動ターン10〜11`＝「21点を10〜11ターン目に叩き込める」。

**既存の条件処理の実態と限界**（実装確認・2026-07-12）:
- 別ベクトルに分けているのは**素/進化/超進化/エンハンスの4種のみ**（`classify()`）。それ以外の全条件（奥義/解放奥義/
  覚醒/復讐/スペブ/コンボ…）は **"sit"（状況依存）に一括**され、モード分割せず**最高値＋発動条件リスト（`conds`）**に
  畳まれる。classifyのデフォルトがsitなので**未知条件も取りこぼさない**（0クラッシュの理由）。
- **限界①**: `conds`はモード全体への一括リストで、**どの増分がどの条件か**は紐付いていない（§11.2の理想「各増分に
  条件を添える」は未達）。**限界②**: 条件の難しさ/ターンが未数値化＝上記「発動ターン軸」で埋める。
- **限界③（お膳立て型の要求）**: ローズの「コスト2以下エルフ7枚」は**カードテキストの要求でない**（FF条件はファンファーレ
  だけ）＝`conds`に出ない。**デッキ構築で生まれる要求は別枠**で持たせる必要がある。

**実装状況**: すべて**未実装**（設計合意のみ）。フェーズ1の残ギャップ（§11.8-4）と合わせて着手する。

### 11.10 効果スキーマ（②の作り直し・LLM抽出の型・2026-07-12ユーザーと確定・未実装）

**背景（方針転換）**: 現行の②（`parse_effect` の文字列マッチ）は、自由テキストをルールで解析していて破綻気味。
効果の先頭語が183種・表記ゆれ（割振/割りふり/割り振り）・head が丸ごと文、で**カバレッジ84%止まり＋silentに
落ちる**。ルールは開いた語彙の裾を追えない。**結論（ユーザー）: 自由テキストのルール解析は無理。LLMがテキストを
"閉じたスキーマ"へ写す**。

**分業の原則**: **意味の翻訳＝LLM ／ 算数＝ルール**。
- LLMは各効果を下記の**型付きスキーマ**に落とす（閉じた選択肢＋必要な自由記述）。silent禁止＝収まらない物は必ず
  `その他` へ明示的に落とす。
- 集計（モード分け・最低/最高・発動ターン・除去構造・縦横＝§11.2〜11.9）は**決定的なルールのまま**。壊れてるのは
  文字列推測だけで、設計と算数は生きる。`parse_effect` はほぼ廃止、`build_vector` 以降の集計は残す。
- **運用**: LLMは**ビルド時に1回**走らせて結果を保存（§11.2 一次データ）＝都度LLMでなく決定性を保存で担保。**人が
  直せる**（§8共著・card_note式）。**コスト・素スタッツ・進化/覚醒ターンはDB/rules.mdの確定値**＝LLMに聞かず計算で重ねる。

**効果スキーマ v1（2026-07-12確定）**: 各カード＝効果のリスト。全効果に `条件:[進化時/FF/覚醒…]`。複数エントリ可
（例: FFと進化時で処理を2つ持つ＝2エントリ）。

```
■ 場
A. 展開      自身{攻, 体, 特性:[無条件]}                      ※攻体=DB・条件付き変化はBへ
             登場:{経路(直接召喚…), どこから, 条件}             ※自身の手札プレイ以外の出方(FF不発)
             随伴:[ {何を: カード名|選択条件(リアニメイトN…), 数, 付与:{攻±,体±,特性}} … ]
B. 処理      対象:{自/相手 × フォロワー/アミュレット/リーダー を複数選択(カード=フォロワー+アミュレット両方)} ／ 繰り返し:N(省略=1)
             範囲:{選択N / ランダムN / 全体 / 全体(自身除く) / 割り振り(総量X)}   ※単体=選択1に統合。フォロワー対象時
             効果:{攻±N, 体±N, 特性付与:[…], ダメージN, 回復N, 破壊/消滅/変身(→カード名)/バウンス}
■ 手札
C. リソース   {動作: 引く/生成, 何枚: N|X(変数), 生成種別: 特定(カード名)/コピー(対象)/参照(自由記述)/変身(→カード名)}
D. 手札処理   対象:{選択N枚 / 全体 / 条件(左からN枚/最高コスト/コストX以下/種族…)}
             効果:{コスト±, 攻±, 体±, 特性付与:[…]}
■ デッキ
E. デッキ処理 対象:{全体 / 条件(…)}   ※非公開なので選択不可
             効果:{コスト±, 攻±, 体±, 特性付与:[…]}
■ 特殊
F. クレスト   {対象: 自/相手, カウントダウン: 有(N)/無, 効果: ネストしたB}
G. 資源      {種類: PP/進化権/超進化権/スペルブースト/土の印/信仰/墓場/カウント, 量: ±N}
H. その他     {記述: 自由記述}   ← 最後の受け皿。カテゴリに収まらない妨害・デッキ生成・変則効果（silent drop禁止）
```

**設計上の決定（理由つき）**:
- **展開＝体を出すだけ**（自身は攻/体/特性のみ・攻体はDB）。条件付きの自己バフ・特性付与は「既存の体を変える」＝
  **B処理(対象=自身)** で表す。動きは全部Bに寄せて統一。**常在/オーラ/供給的な無条件能力（カローンの死者へ守護付与・
  2回攻撃等）は自身の特性に自由記述で**（内部トリガ〜が出たときは発動条件でなく能力の一部）。1回発火の能動効果だけ処理。
- **繰り返し・自身除く**（2026-07-12テスト由来）: 「同じ効果をN回」は処理に `繰り返し:N`（書き直さない）。「場の他の
  フォロワーすべて」は範囲 `全体(自身除く)`。反復・自身除外を条件に混ぜない。
- **条件で効果が動く3系統**（2026-07-13テスト由来・ユーザー確定）: ①**加算**「さらに」＝別エントリ（下流が足す）
  ②**X型**「Xは◯◯の枚数」＝数値フィールドに `"X:<数えるもの>"`（計算せず数える対象を書く）③**変化（置き換え）**
  「◯◯。□□なら代わりに△△」＝基本エントリに `変化:{条件, 変わるフィールドだけ}`（値だけ2→4も範囲ごと単体→全体も
  同じ形・書かないフィールドは基本を引き継ぐ・段階型はリスト）。別エントリに割ると下流が加算して過大になるので割らない。
  旧parse_effectの「置換は最大化」の後継。集計は最低値=基本／最高値=基本に変化を上書き＋変化条件が§11.2の増分条件。
- **引くのフィルタ**: 「デッキからフォロワーを引く」等のサーチはリソースに `何を:<フィルタ>`。**アクトの起動コスト**は
  `条件:["アクト(コストN)"]`（PP産出と混同しない）。
- **アミュレットは自身={特性:[…]}（攻体なし）**（2026-07-13テスト由来）: 【カウントダウン_N】（自身の寿命）は
  `カウントダウンN` として特性へ。トリガ能力も特性へ。スペルのみ自身=null。
- **登場＝自身の手札プレイ以外の出方**（2026-07-13サンダルフォン由来・ユーザー訂正）: 直接召喚（デッキで働き条件で
  自動的に出る）は随伴（別の体）でなく `登場{経路, どこから, 条件}`。非手札プレイ＝FF不発。出た後の付随効果
  （クレスト獲得・自身が手札に戻る）は `条件:["直接召喚された時"]` の別エントリ。下流ではコスト0の別プレイ版（モード）になる。
- **対象に「自身」を追加**: 自己バフ・自傷・自分を手札に戻す等はこれ（「自フォロワー選択1」に逃げていた癖の根治）。
- **処理は盤面とリーダーを統合**（対象を複数選択）。マーウィン（盤面優先で盤面＋リーダーに割り振り）・シャクドウ
  （全体＋顔）を1効果で表せる。対象で「対フォロワー＝除去＝生存レース／対リーダー＝打点＝キルレース」の振り分けは
  下流が保つ（§11.4）。**表現は統合・意味の振り分けは下流**。
- **特性＝キーワード＋自由記述の横並べ**。突進/疾走等の「攻撃力を盤面/顔に振る＋代償」は変換せず**事実として記録**、
  行き先と代償は下流の解釈（§11.4静的境界・§11.7）。バリアも特性の1つ。
- **ダメージ/回復/体は別プリミティブ**（rules.md参照）。バリアはダメージだけ防ぐ・体−は貫通・回復は最大まで、で
  相互作用が違うため1つに潰さない。
- **手札とデッキを「得る/生成」と「処理」に分割**（場のA/Bと同じ対称）。デッキは非公開なので処理の対象に選択Nが無い。
- **クレストは別枠**（遅延カウントダウン＋ネストした効果を持つ構造ゆえ）。**資源は貯める燃料**（打点でも体でもカードでも
  ない・他カードを動かす）。**土の印=盤面/スペブ=手札と居場所は違うが同じ燃料扱い**。
- 資源に見えて実は**条件**（≠資源）: 覚醒/エンハンス/融合/連携/アクセラレート/結晶/土の秘術。これらは`条件:`側。
- **お膳立てフィニッシャー**（ローズ→薔薇の閃撃）は **C.リソース生成種別=変身(→薔薇の閃撃)** で表れ、生成物のカード名から
  そのベクトルを参照＝§11.9のお膳立てがこの型で自然に解ける。

**残・要フォロー**: ①デッキに"加える"（山札変換・デッキ生成）はEの処理に収まらない → 当面`その他`。②`その他`枠は

**集計(B3)の追加決定（2026-07-15ユーザーと確定・vector.py実装済み）**:
- **変化（置き換え）はリソースにも付く**: 「1枚を引く。融合していたなら1枚ではなく2枚」はB処理と同じ
  `変化:{条件, 変わるフィールド}` で書く。処理限定だったのはスキーマ穴（花園の導きでLLMが加算2エントリに
  割って過大になった実例）。
- **カード枚数＝実カードのみ・トークン生成は別軸**: 引く=カード枚数／生成=「トークン生成」軸＋生成対象名。
  トークンの価値は実カードと別物（薔薇の閃撃は強い・ノイズは弱い）で、値はデッキ文脈で決まるため混ぜない。
- **融合＝手札の素材消費**: 融合条件を持つモードは天井側にカード枚数-1（最低。実枚数は手札次第で見積り非対象）。
- **盤面は体のリストで保持**: 体数と最大単体の2値では「9/1+1/1×3」と「3/3×4」を区別できない。
  出る体ごとに（名前・攻・体・数・条件）を持ち、合計スタッツ・縦横はそこから導出（早すぎるcollapse禁止＝§11.2）。
