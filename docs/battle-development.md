# シャドバWB開発資料から採用する設計（2026-09-14調査）

## 一次資料で確認できること

- WBでは対戦処理をサーバーに集約し、処理結果から演出情報を作って画面へ返す。カード能力と演出のデータも分割した。開発用ブラウザでカード操作でき、画面側の演出実装を待たずに能力を試せる。画面なしの自動検査も可能になった。資料の約10ms/対戦という数字は公式環境の事例値であり、本実装の性能目標や計測値ではない。[Cygames U/Day Tokyo 2025資料、p58–60・67–70](https://speakerdeck.com/cygames/cygames_202512_udaytokyo2025)
- フォローアップでは、前作はクライアントのカード能力とサーバーの検証を二重に維持する必要があり、WBの処理集約で長期運用の実装コストを減らし、拡張への対応速度が上がったと説明する。通信待ちを演出に合わせて調整したが、演出がゲームルールを決める構造にはしていない。[Cygames Engineers' Blog、2025-12-25](https://tech.cygames.co.jp/archives/3706/)
- 旧Shadowverseの2019年資料では、能力を「動作・発動時点・条件・対象・数値など」の5要素へ分解。部品単独、組み合わせ、過去に問題のあった組み合わせ、自動対戦の4種類で検査。複雑な組み合わせを厚く検査し、能力処理後と行動完了後の途中状態も比較している。これは旧作資料なので、WBの内部実装そのものとは断定しない。[Cygames CEDEC 2019資料、p60–66・72・79–81](https://speakerdeck.com/player/da5138167c59419daaa7cecd1f5ed3b7)
- 開始盤面と操作列を記録して再生・比較する方法も説明されている。ユーザー承認を必須にする根拠ではない。本プロジェクトでは利用者の明示方針に従いAIがケースを作成する。[2019年公式フォローアップ](https://tech.cygames.co.jp/archives/3304/)

## 今回の実装で守る境界（資料を踏まえた本プロジェクトの設計判断）

1. **対戦本体**は状態＋行動から次状態と構造化された出来事を計算する。時刻、画面、アニメーション待ち、外部通信に依存させない。記録OFFでも全く同じ乱数・発動順・結果になる。
2. **カード定義**はタイミング、条件、対象、値、処理の列を記述する。カードIDごとの条件分岐を本体へ足し続けない。型/項目検査と実行処理の対応を一箇所へ集め、未対応指定を拒否する。
3. **画面**は結果の出来事を順に短い動きとして表示する。演出OFFは即座に終了状態を表示。ON/OFF・速度・巻き戻し・中断は表示だけに作用し、ゲーム乱数と判断には関与しない。
4. **カード追加の完了条件**は代表デッキの40枚＋生成先カードの依存関係が全て対応すること。分解した効果ごとの通常・境界例3～5件に加え、デッキ固有の連鎖、複数発動、場/手札上限、終局を検査する。単発効果だけ対応したカードをデッキ対応済みにしない。

## 今回反映した変更と追加場所

- `battle.py` が状態・通常行動を持ち、`battle_rules.py` が選択・条件・発動の待ち列・追加作用を扱う。
  `emit()` は表示記録専用。記録を切っても発動と乱数は変わらない。
- `battle_meta_cards.py` に今回の2構築31種と必要な生成先7種を宣言した。既存1種と重複するため、
  対応実カードは50種から87種へ増えた。モード・別形態・条件・対象・参照先を登録時に検査する。
- 手札と敵の選択を `choices` の異なる項目へ保存する。入れ子の選択用途の衝突、
  スペルの対象不足・重複選択を拒否し、選択済み対象が消えても勝手に別対象へ変えない。
- 登場・進化・捨てる・回復・ターン開始終了の発動を予約する。同時に始まった終了時能力を
  先に予約し、その処理で生じたラストワードを後ろへ積む。公式ゾンビQ&Aを回帰例にした。
- クレストの回数制限とゾーイの保護期限を状態に保存する。初期状態指定・記録再生でも保持する。
- `battle_decks.json` に出典・確認日・カード枚数を保持する。40枚と生成先の対応が揃った構築だけ開始する。
- `animation.js` は確定した盤面に出来事の演出を重ねる。演出取消は状態へ影響させない。

### 次のカードを追加するとき

1. 対象構築の40枚・生成先・クレストや別形態の本文を確認し、DBのユーザー注記も読む。
2. 共通部品で表せる効果を定義へ追加する。未知の動作だけ共通処理と入力検査を同時に追加する。
3. 実行前に通常・境界・拒否の期待値を固定する。関連カードとの連鎖と記録ON/OFFも検査する。
4. 本文と参照先能力の識別値を登録し、構築を最初から終局まで動かして保存再生を確認する。
5. 人向け画面でも選択と処理理由が追えることを確認する。未対応を無効果へ落とさない。

公開開発資料は正確なカードルール順序の根拠ではない。今回も実機の全組合せ比較は未実施。
特に捨てたときの誘発と元のファンファーレ後半の前後は公開資料で確定できず、現在は元の能力の後へ予約する。
この未確認点と検査結果は[対戦ラボの対応範囲](battle.md#出典と未確認の範囲)へ残している。
