# シャドバWB開発資料から採用する設計（2026-09-14調査）

## 一次資料で確認できること

- WBでは対戦処理をサーバーに集約し、処理結果から演出情報を作って画面へ返す。カード能力と演出のデータも分割した。開発用ブラウザでカード操作でき、画面側の演出実装を待たずに能力を試せる。画面なしの自動検査も可能になった。資料の約10ms/対戦という数字は公式環境の事例値であり、本実装の性能目標や計測値ではない。[Cygames U/Day Tokyo 2025資料、p58–60・67–70](https://speakerdeck.com/cygames/cygames_202512_udaytokyo2025)
- フォローアップでは、前作はクライアントのカード能力とサーバーの検証を二重に維持する必要があり、WBの処理集約で長期運用の実装コストを減らし、拡張への対応速度が上がったと説明する。通信待ちを演出に合わせて調整したが、演出がゲームルールを決める構造にはしていない。[Cygames Engineers' Blog、2025-12-25](https://tech.cygames.co.jp/archives/3706/)
- 旧Shadowverseの2019年資料では、能力を「動作・発動時点・条件・対象・数値など」の5要素へ分解。部品単独、組み合わせ、過去に問題のあった組み合わせ、自動対戦の4種類で検査。複雑な組み合わせを厚く検査し、能力処理後と行動完了後の途中状態も比較している。これは旧作資料なので、WBの内部実装そのものとは断定しない。[Cygames CEDEC 2019資料、p60–66・72・79–81](https://speakerdeck.com/player/da5138167c59419daaa7cecd1f5ed3b7)
- 開始盤面と操作列を記録して再生・比較する方法も説明されている。ユーザー承認を必須にする根拠ではない。本プロジェクトでは利用者の明示方針に従いAIがケースを作成する。[2019年公式フォローアップ](https://tech.cygames.co.jp/archives/3304/)

## 今回の実装で守る境界（資料を踏まえた本プロジェクトの設計判断）

1. **対戦本体**は状態＋行動から次状態と構造化された出来事を計算する。時刻、画面、アニメーション待ち、外部通信に依存させない。記録OFFでも全く同じ乱数・発動順・結果になる。
2. **カード定義**はタイミング、条件、対象、値、処理の列を記述する。カードIDごとの条件分岐を本体へ足し続けない。型/項目検査と実行処理の対応を一箇所へ集め、未対応指定を拒否する。
3. **画面**は結果の出来事を順に短い動きとして表示する。演出OFFは即座に終了状態を表示。ON/OFF・速度・巻き戻し・中断は表示だけに作用し、ゲーム乱数と判断には関与しない。
4. **カード追加の完了条件**は代表デッキの40枚＋生成先カードの依存関係が全て対応すること。カードごと通常・境界例3～5件に加え、デッキ固有の連鎖、複数発動、場/手札上限、終局を検査する。単発効果だけ対応したカードをデッキ対応済みにしない。

## 現行実装の優先改善

### 優先1：誤った対象への作用を防ぐ（再現済み）

`battle.py:validate_cards` は選択対象種類を最上位のeffectsだけで集計する。`if.effects` 等の下に「敵を選んで1ダメージ」「味方を選んで1回復」を入れると検査をすり抜ける。`targets` は chosen_* に対し選択IDの存在しか確認せず、同じ敵を回復してしまう。

再現定義：`effects=[{'op':'if','effects':[{'op':'damage','target':'chosen_enemy','amount':1},{'op':'heal','target':'chosen_ally','amount':1}]}]`。敵体力2/味方体力1で敵を選んで使用すると、敵は2へ戻り味方は1のまま。

最小修正は再帰検査と、通常効果＋エンハンスを合成した実行列に対する検査。複数選択が必要になった時点で `choices` を選択項目IDごとに持たせる。選択時/解決時の適格性はカードルールとして区別し、再解決で勝手に別対象を選ばない。

### 優先2：発動・動的値を共通部品にする（未対応能力の拡張上の課題）

- 現行はファンファーレ/進化/ラストワード等の固定列のみ。場にある間の「別カードをプレイした」「召喚した」「進化した」「破壊された」「回復した」発動や、紋章等の永続効果は表せない。発生した出来事を受ける発動条件と、確定した発動を並べる処理列を本体に持たせる。`emit()` は記録OFFだと何もしないため、ルールの発動判定をemitへの依存で実装してはいけない。
- 現行の値は固定整数、条件はawakening/combo3/max_pp10のみ。手札枚数・特定分類の破壊数・消費資源・今回の対象等を読む限定された値式が必要。任意evalやカード専用Python式は使わない。「いつの値を読むか」を明示し、対象ごとに計算が変わる効果と発動時に一度確定する効果を区別する。
- 永続/回数制限/ターン限りの付与効果には発生源、所有者、有効期限、使用回数を保存し、巻き戻しでも保持する。分類・破壊履歴もカード本文から推測せず明示する。

### 優先3：処理順と保存互換性を固定する

`settle` は作用のまとまりごとに死亡処理し、`pending` はラストワードだけを後でFIFO解決する。環境デッキの新発動を追加する際は、同時ダメージの対象確定、発動候補の確定、死亡判定、発動列の優先順、途中勝敗の区切りをテストで固定する。現行の動作を全能力へ一般化して正しいとは断定しない。

公開資料は正確なルール順序の根拠にはならない。新しい順序の必要性は対象カード本文/公式ルールで確認する。処理方式を変えたら保存形式版とルール版を区別し、旧リプレイを黙って別の意味で成功扱いしない。

記録には連番・発生源ID・対象ID・処理種別・変更前後・原因となった処理のIDを持たせると、表示、途中状態の比較、再現調査が同じ記録で行える。記録を外しても発動列自体は同じであることを検査する。
